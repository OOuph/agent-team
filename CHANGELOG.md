# Changelog

The living description of the loop is [SCHEME.md](SCHEME.md); this file records when it changed and why. Rule: a pull
request that changes behaviour (roles, phases, states, tools, policies) updates SCHEME.md and adds a line here in the same
PR, citing the friction records (F-xxxx) or the owner decision behind it. The retro role proposes, the developer writes
the PR, a human merges.

## 2026-11-27

- A cycle's spend is the sum of its own runs (`Store.spent_by_cycle`: the rows of `spend` whose run id starts with the cycle id), not the difference of `spent_today()` at its end and its start. A cycle that crossed midnight UTC showed a negative number — ai-battles `20261126T2350`: «$-345.13» for a real 12.64; the same on 20, 22 and 24.11. Only `cycles.spent_usd`, the cycle's summary line and `team status` were wrong; the `spend` table, the day cap and billing were not. tests/test_cycle_spend.py.

- A task never waits in silence for a dependency that was rejected (hittheline 26.11, 20:07–21:48 UTC: three ready tasks did not start, the developer's lane closed in a second without a line). One PO answer had closed T-0001…T-0008 and created their successors with `depends_on` on the closed numbers — the PO could neither change a task nor name a task of the same answer — and `unmet_dependencies` counted a rejected dependency as unmet for ever. Now: (1) `dead_dependencies` — a dependency that is rejected with nothing in its place, or does not exist; the task still does not start, but every cycle logs a WARNING with both numbers, and once per set of dead ids the dispatcher writes `task.dependency_dead` and asks the PO; (2) one PO answer cannot make such a dead end: `depends_on` may be the exact title of a task of the same answer (as onboarding already allowed), `close_tasks` takes `replaced_by` (an id or such a title), and `Cycle.settle_dependencies` moves every dependency on a rejected task to its replacement or drops it (`task.dependency_moved` / `task.dependency_dropped`, a line in the digest) — for the new tasks and for older open tasks that waited for a task the answer closed; a rejected dependency with `replaced_by` is judged by its replacement from then on; (3) `edit_tasks` in po-decision: the PO changes `depends_on` of an open task in place; (4) onboarding of a site: generator, pages, sitemap and markup are `ops`, not `feature` (card and the sample plan) — a `feature` waits in `proposed` for evidence from people, which is why the PO re-created those tasks. tests/test_dead_dependencies.py.

- Seats no longer stand idle in silence (ai-battles 26.11, 19:13–22:00 UTC: cycles ran, nothing started; owner: «почему не тратятся токены»). Three causes, each without a line in the log. (1) The open-task check dropped real tasks: `duplicate_task` treats «same role, same `not_before`» as one slot — a rule written for scheduled posts — and when the PO scheduled three developer tasks for 00:05 UTC (spend was above 80 % of the daily cap) two of them were skipped as duplicates of the first. The slot rule now applies to `SLOT_ROLES` (marketer) only; the title rule is unchanged. (2) A lane whose task was not startable ended without a word: it now logs «T-xxxx not started: scheduled for … (`not_before`)» (or: a run holds it, its question is open, it waits for a dependency), and a cycle that started nothing writes one `execute.idle` event with the list. (3) A task for the role `artist` — the product's word for `designer` — had no seat and was never picked: `Cycle.normalize_roles` renames an alias (`ROLE_ALIASES`) with a history note, and a ready task for a role that has no seat or cannot be run gives a warning and one `environment_error` observation for the PO; `team task new --role` takes the alias and refuses an unknown role (exit 2). tests/test_idle_seats.py.

## 2026-11-25

- Batch deploy for service products (owner 25.11: «чтобы выкладка шла пачкой, раз в цикл, а не после каждой задачи»). On ai-battles 25.11 the dispatcher deployed 52 times, once after every merge; each deploy holds the live host exclusively and cuts the matches of live players, and 17 of them waited for play-tests, 124 minutes in all, with the repository lock held. `deploy: {batch: true}` in product.yaml (off by default): merges go on as tasks finish, the host is switched once per cycle — at the end of the execute phase, on the head of the base branch, under the repository lock. A merged task carries `deploy_pending` and is neither reviewed nor called deployed until the batch that takes it; `deploy.batch_max_wait_min` (45) bounds the wait (the next merge or a timer deploys earlier); the next cycle's review phase starts with what a dead or chained cycle left. A batch that fails because of the host or the transport is retried by the next batches (3 times, one `environment_error` observation); any other failure goes through the per-task path — each waiting task's own merge commit in merge order — which blocks the first that does not deploy, as before. `team deploy` by hand is unchanged. team/lanes.py invariant 5 reworded; SCHEME §3 «Выкладка пачкой».
