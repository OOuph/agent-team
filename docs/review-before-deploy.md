# Видимое изменение: ревью и просмотр владельца до выкладки игрокам

Срез 5 большой доработки (владелец 26.11). До него порядок у игры был `in_progress → released` (слито и выкачено)
`→ review → accepted`: игроки видели изменение раньше, чем его кто-либо оценил. В ночь 25–26.11 команда переложила
первый экран `ai-battles` без новой функции, ревью приняло по совпадению с макетом, владелец увидел это уже на сайте.

## Что сделано в коде (не требует root)

Настройка `cycle.visible` в `product.yaml`, оба ключа по умолчанию выключены.

1. **Признак у задачи.** PO ставит `visible: true` (меняется то, что видит игрок), `redesign: true` (меняется
   расположение, размер или вид существующего экрана) и `new_function` (что игрок сможет делать нового). Поля есть в
   схеме решения PO и сохраняются на задаче.
2. **`review_before_merge: true`.** Задача с `visible: true` после отчёта исполнителя не сливается: коммит остаётся
   на ветке `task/<id>`, задача идёт в `review` с пометкой `pre_merge`. Ревью поднимает сервер локально из этого
   коммита (`playtest.start(force_local=True)`), тестировщик играет на нём; живой сайт служит видом «до».
   Вердикт «принято» сливает ветку и ставит задачу в очередь обычной выкладки, состояние сразу `accepted`.
   Вердикт «не принято» возвращает задачу исполнителю; на сайте ничего не появлялось.
3. **`redesign_gate: true`.** Задача с `redesign: true` без `new_function` не создаётся; владельца никто не
   спрашивает, в дайджесте PO остаётся строка, событие `task.redesign_refused`.
4. **Карточки** PO, ревьюера и тестировщика содержат принцип владельца «редизайн делаем только при новом
   функционале»: перекладка существующего экрана без новой функции получает «не принято», даже при совпадении с макетом.

Порядок состояний видимой задачи: `in_progress → review (pre_merge) → accepted (слито) → выкладка пачкой → measured`.
Невидимые задачи идут как раньше.

## Отложенный замысел: просмотр владельца на сервере игры

**Не строим.** Решение владельца 26.11.2026 на вопрос о предпросмотре: «я не могу каждое изменение смотреть, давай пока
опираться на правило "не перерисовывать без необходимости"». Действий от root не нужно. Вместо просмотра действует
правило: PO не заводит задачу, которая только перекладывает существующий экран (диспетчер такую не создаёт и никого не
спрашивает), ревьюер возвращает такую правку с причиной `redesign_without_function`. Исключения: исправление явной
поломки (наезд, выход за границы, нечитаемость) и элемент новой функции в существующей раскладке. Схема ниже оставлена
на случай, если решение изменится.

Ревью до слияния закрывает оценку ролью. Просмотр владельцем требует адреса, по которому новая версия доступна
до переключения. Наименьшая рабочая схема:

1. **Третий экземпляр сервиса «предпросмотр».** Сейчас у игры два цвета (`<slug>-a`, `<slug>-b`): выкладка
   поднимает новый релиз на свободном цвете и переключает на него nginx. Свободный цвет нужен каждой выкладке,
   поэтому предпросмотр на нём мешал бы обычным выкладкам невидимых задач. Шаблон systemd `agent-team-svc@.service`
   допускает любое имя экземпляра: добавляется `<slug>-p` на своём порту (`PREVIEW_PORT` в `<slug>.conf`).
2. **Отдельные данные.** Экземпляр предпросмотра получает `DATA_DIR=…/data-preview` (копия боевых данных на момент
   подъёма), чтобы новая версия не писала в боевые файлы и SQLite.
3. **Команды скрипта выкладки.** `deploy-service.sh <slug> --preview --sha <commit>`: релиз, сборка, запуск
   `<slug>-p`, проверка здоровья; nginx-upstream боевого сайта не трогается. `--preview-stop` гасит экземпляр.
4. **Адрес.** Вариант А: поддомен `preview.<хост игры>` со своим сертификатом и вхостом на `PREVIEW_PORT`. Вариант Б:
   тот же домен, nginx `map $cookie_team_preview` выбирает upstream; ссылка `https://<хост>/?team_preview=<ключ>`
   ставит cookie. Вариант Б не требует DNS и сертификата, но правит боевой вхост.
5. **Диспетчер.** После вердикта «принято» у задачи с `redesign: true` (или у любой видимой, по решению
   владельца) задача не сливается, а идёт в `waiting_owner`; диспетчер собирает ветку предпросмотра (основная ветка
   плюс ветки ждущих задач), зовёт `--preview`, шлёт владельцу ссылку и снимки «до и после». Ответ владельца
   сливает задачу или возвращает её исполнителю.

## Что требует root

- Установить обновлённый `deploy/service/deploy-service.sh` в `/opt/agent-team/bin/` на сервере игры.
- Добавить `PREVIEW_PORT` в `/etc/agent-team/services/<slug>.conf`.
- Вхост nginx: новый `server` (вариант А) или `map` и второй upstream в боевом вхосте (вариант Б), `nginx -t`, reload.
- Вариант А: `certbot` для поддомена.

## Что решает владелец

1. Адрес предпросмотра: поддомен (нужна DNS-запись) или cookie на основном домене.
2. Что ждёт его просмотра: только задачи с `redesign: true` или каждое видимое изменение. Второе остановит
   видимую работу на время его отсутствия.
3. Что делать, если ответа нет N часов: держать скрытым или выкатывать.
4. Данные предпросмотра: копия боевых (гаражи и аккаунты видны) или пустые.
