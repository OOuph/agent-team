# agent-team — схема петли, которую запускаем (единое описание)

Статус: утверждена владельцем 02.11.2026 (решения 02.11 п. 1–15 в `decisions.md` vault). Это единственное полное описание
того, что работает; ТЗ v2 в vault — история проектирования, README — команды. Меняется только вместе с решением владельца.

## 1. Что это

Диспетчер (Python: файлы + git + SQLite) ведёт продукт силами ИИ-ролей на Claude Code. Роли — короткие прогоны
`claude -p` без памяти; между собой не разговаривают, всё общение — записи в `products/<slug>/` (задачи, вопросы,
наблюдения, ревью, дайджесты). Диспетчер — программа: очередь, лизы, бюджеты, фазы, разрешения, журнал. Решения о продукте
принимает роль PO внутри `VISION.md`; за пределами VISION (цели, каналы, бюджет, обещания, аккаунты, домены) — вопрос владельцу.

## 3. Цикл (cron раз в час на каждый продукт, `team cycle`; чаще — по `cycle.every_min` продукта)

| Фаза | Что делает | Модель |
|---|---|---|
| collect | снимает истёкшие лизы; забирает `/_team/metrics.json` сайта; **собирает обратную связь** (GitHub Issues, ответы/упоминания Bluesky) в наблюдения и **отвечает людям** (роль support, в рамках VISION); раз в `cycle.persona_every_h` (12 ч) — персоны; раз в 12 ч — программная SEO-проверка | persona |
| review | задачи `released` (после паузы на деплой, `cycle.review_after_min` = 6 мин; каждая — своя дорожка: ревью идут рядом друг с другом, с triage и с execute и не задерживают их, «Параллельные дорожки» ниже) → reviewer (у продукта `game` — tester, §11) → `accepted` / `in_progress` (первый fail) / `blocked` + вопрос PO (второй fail, `cycle.max_review_fails` = 2); о вердикте `inconclusive` — «Правило неопределённого ревью» ниже | reviewer / tester |
| triage | при новых наблюдениях, вопросах к PO, простое команды или **простое разработчика** (нет его задач; не чаще раза в `cycle.dev_idle_po_every_h` = 12 ч, PO ставит дефекты и задачи качества) → PO; в начале фазы — карточки `hypothesis_readout` для фич, чей `read_on` наступил, и **задачи постоянных направлений**, которым пришёл срок: их диспетчер создаёт сам, без прогона PO («Постоянные направления» ниже) | po |
| execute | по одной задаче на место (`cycle.execute_slots`), места работают одновременно — каждое в своей дорожке («Параллельные дорожки» ниже); developer — в собственном чекауте задачи (`git worktree`, `data/work/<slug>/wt/<id>`; повтор задачи продолжает существующую ветку `task/<id>` с коммитами прошлой попытки, слив в неё base; при конфликте слияния — слияние с приоритетом стороны прошлой попытки, коммит прошлой попытки остаётся в истории ветки) → коммит → **merge в main + push** (под замком репозитория продукта; конфликт слияния возвращает задачу автору, цикл идёт дальше) → droplet публикует ≤ 5 мин → `released`; marketer → черновики (`team-publish` в режиме черновика) → editor → при revise одна доработка маркетолога → editor → диспетчер публикует одобренное (текст поста — в таблицу `posts`) → `accepted`; marketer с `plan: true` → пишет `marketing-plan.md` в рабочей папке → диспетчер копирует в `products/<slug>/` → `accepted` без поста (файла нет или < 200 символов → вопрос PO); analyst-задача → `done` | developer / marketer / analyst |

Каждые 6 ч (`measure_every_h`): analyst по метрикам, эффект задач → `measured` → `done` | analyst |

**Модели и предел одного прогона по ролям** (владелец 23.11). Модель роли: `claude.models.<роль>` в `team.yaml`, для продукта `models.<роль>` в `product.yaml` (имя или псевдоним, который принимает `claude --model`). Предел расхода одного прогона роли: `run_caps.<роль>` в `product.yaml`, ниже `budget.run_caps.<роль>` в `team.yaml`; без них действует предел вызывающего кода (у PO 2 доллара, у задачи `budget_usd`, иначе `budget.max_usd_per_run`). Роль, переведённую на более дорогую модель, переводят вместе с её пределом: прогон, упёршийся в предел, обрывается без результата. Дневной предел продукта действует всегда.

**Каденция цикла** (владелец 20.11: «в режиме разработки если простой — запускай цикл ранее»; трение F12 запуска ai-battles; `team/cadence.py`). По умолчанию продукт работает раз в час: cron `7 * * * *` → `run-cycle.sh` → `team cycle --product all`. Продукту в активной разработке в `product.yaml` ставится `cycle: {every_min: N}` — целое число минут от 5 до 60; другое значение — ошибка загрузки продукта с именем файла; исключение не перехватывается, поэтому с таким `product.yaml` не стартует `team cycle` ни для одного продукта, пока файл не исправят (сверка 21.11). Вторая строка cron одна на все продукты: `*/5 * * * * bash run-cycle-fast.sh` → `team cycle --due`. Она запускает цикл продукта, если у него есть `cycle.every_min`, нет STOP-файла (продукта или общего), продукт не на паузе и не в онбординге, и с завершения его последнего цикла (поле `finished` таблицы `cycles` в `team.db`, кто бы его ни запустил — часовой вход или быстрый) прошло не меньше N минут; продукт без завершённых циклов запускается сразу. Продукт без настройки быстрый вход не трогает и ничего не пишет в его хранилище. Быстрый вход не ждёт часового прохода: у каждого продукта свой замок, см. «Блокировки циклов» ниже. Шаг cron 5 минут — точность каденции: при `every_min: 10` цикл стартует через 10–15 минут после конца предыдущего. Работа уровня фреймворка (проверка отката, сбор трений, ретро, ответы внешнему критику) и запись `data/framework/last-good` остаются за часовым проходом. Дневной лимит `budget_usd_per_day` общий для всех циклов продукта: при частой каденции он расходуется быстрее, после исчерпания циклы идут без запусков ролей. `team status <slug>` показывает строку `cadence: cycle every 10 min · next in 4 min` (или `due now`, `cycle running now`, причину остановки) либо `cadence: hourly`. Вернуть продукт на часовой ритм — убрать `cycle` из product.yaml; crontab при этом не меняется.

**Постоянные направления** (владелец 21.11, первая игра: «постоянные направления — придумывать необычные механики и тестировать каждую до входа в игру; автоматическая балансировка»; `team/standing.py`). Это работа, которую нельзя закрыть одной задачей: к ней нужно возвращаться. До 21.11 такая работа держалась на памяти PO и на разделе, написанном руками в VISION одного продукта. Теперь направление — запись в `product.yaml`:

```yaml
standing:
  - id: balance            # уникальный; задача направления несёт поле `standing: balance`
    role: game-designer    # кто исполняет: developer, designer, game-designer, tester, marketer, analyst
    type: design
    every_h: 24            # новая задача не чаще, чем раз в столько часов (1…1440), счёт от создания предыдущей
    title: "…"
    problem: "…"
    scope: "…"
    acceptance: ["…", "…"]
    priority: P2
    # необязательные: size (S), goal, from_stage (этап, с которого направление работает), docs (пути документов в репозитории, которые роль ведёт и получает в промпте целиком)
```

Ключа `standing` нет — действует встроенный список профиля: два направления у `profile: game` (§11), ни одного у остальных профилей, то есть сайты работают как раньше. Пустой список `standing: []` выключает направления. Запись с `id` встроенного направления наследует от него все поля, которые не задала сама: `- {id: balance, every_h: 12}` меняет только интервал. Ключ, заданный явно, заменяет встроенный список целиком: встроенное направление, которого в списке нет, выключено. Запись с ошибкой (нет `id`, неизвестная роль, `every_h` вне диапазона, пустой `acceptance`, повтор `id`) пропускается: ошибка пишется в журнал уровнем ERROR и строкой `standing config: …` в `team status`, остальные направления и цикл продукта работают.

Срок задачи решает `standing.due(product, store, now)`. Задача направления нужна сейчас, если выполнены оба условия: ни одна задача с полем `standing: <id>` не открыта (открытой считается задача в любом состоянии, кроме `accepted`, `rejected`, `done`, `measured`) и последняя такая задача создана не меньше `every_h` часов назад либо не создавалась никогда. Направление ждёт, пока этап продукта не дойдёт до его `from_stage`; так же действуют ворота `phase_gates: {standing: M1}` (все направления) и `phase_gates: {standing.<id>: M2}` (одно). Задачу создаёт сам диспетчер в начале фазы triage (`Cycle.create_standing_tasks`): состояние `ready`, `created_by: dispatcher`, поле `standing: <id>`, поле `docs` из записи, событие `standing.created` с именем направления и номером цикла. Прогон PO для этого не нужен; если PO в этой фазе запускается, он уже видит новую задачу в бэклоге и блок STANDING DIRECTIONS (направления, интервалы, открытая задача или время до следующей). Задачи не создаются в сухом прогоне (`--dry-run`), при STOP-файле, `paused` и незавершённом онбординге. Пока задача направления открыта, вторая не создаётся — ни диспетчером, ни PO: в схеме `po-decision` у ready-задачи есть необязательное поле `standing`, задача PO с ним считается задачей направления и отбрасывается как дубль, если у направления уже есть открытая (`task.duplicate_skipped`). Задача, созданная руками с той же целью, считается задачей направления, когда в её YAML в `products/<slug>/backlog/` стоит поле `standing: <id>`. `team status <slug>` печатает строку на каждое направление: `standing balance: every 24 h, game-designer · open T-0031 (ready)`, `… · next in 5.2 h (last T-0031 created 18.8 h ago)`, `… · due now (never created)` или `… · waits for stage M1 (now M0)`.

**Блокировки циклов** (20.11, трение F17 запуска ai-battles; `team/locks.py`). До 20.11 оба cron-входа оборачивали весь процесс `team cycle` в один `flock -n data/cycle.lock`: часовой проход 14–15 минут сидел в первом продукте (`agent-team`), и всё это время игра с каденцией 5 минут стояла в `due now` — около четверти времени. Теперь замки берёт сам `team cycle` (тот же `flock(2)`, что у утилиты `flock`, поэтому скрипты и диспетчер видят друг друга), а скрипты `run-cycle.sh` и `run-cycle-fast.sh` его не оборачивают:

| Замок | Кто держит | Что защищает |
|---|---|---|
| `data/locks/product-<slug>.lock` | исключительно — цикл этого продукта, из любого входа | хранилище продукта (`products/<slug>/`), его клон `data/repos/<slug>`, рабочую папку `data/work/<slug>` с чекаутами задач `data/work/<slug>/wt/`: один цикл на продукт (что делят дорожки внутри этого цикла — «Параллельные дорожки» ниже) |
| `data/locks/hourly-pass.lock` | исключительно — `team cycle --product all` | часовую работу фреймворка (проверка отката, регистр трений, ретро, ответы критику) и запись `last-good`: один проход за раз |
| `data/cycle.lock` | совместно — каждый процесс `team cycle` на всё время работы; исключительно — то, что заменяет код диспетчера | чекаут диспетчера: код не меняется под идущим циклом |
| `data/locks/code-update.gate` | исключительно — обновление кода, пока ждёт и работает | очередь обновления: у `flock` нет приоритета писателя, без ворот обновление при циклах каждые 5 минут могло бы ждать бесконечно |

Порядок взятия на старте цикла один: ворота → замок кода → проход → продукт. Исключения: самослияние берёт ворота и исключительный замок кода, уже держа замки прохода и продукта (свою совместную блокировку кода оно перед этим отдаёт), а канарейка берёт замок второго продукта под замком первого. Правила: `--product all` идёт по продуктам по очереди и **пропускает** продукт, чей цикл уже идёт в другом процессе (строка `cycle <slug>: skipped — its cycle is already running` в логе), остальные отрабатывает; второй часовой проход при идущем первом не стартует (код выхода 75). `--due` запускает due-продукт, если свободен его собственный замок, не дожидаясь чужих; под замком продукта due проверяется ещё раз (пока этот процесс занимался другим продуктом, цикл мог завершить соседний вход). Идентификатор цикла — минута UTC: если два входа стартовали в одну минуту, второй пропускает продукт, у которого цикл с таким id уже есть. Ретро пишет задачи в хранилище продукта-фреймворка, поэтому берёт его замок; занят — ретро переносится на следующий проход.

Код диспетчера меняют три операции, все под исключительным `data/cycle.lock`: **обновление** — `update-code.sh` (его зовёт `sync.sh`): закрывает ворота, с этого момента новые циклы не стартуют (`team cycle` выходит с кодом 75, следующий тик cron смотрит снова), ждёт конца идущих циклов (`UPDATE_WAIT_S`, 3600 с), делает fast-forward и открывает ворота; **откат сторожа** — `watchdog.sh` берёт замок без ожидания (занят — значит, цикл идёт, сторож выходит) и держит его до конца `git reset`, отпуская перед запуском прохода; **самослияние** продукта `agent-team` — `Cycle.update_own_code`: цикл отдаёт свою совместную блокировку, закрывает ворота, ждёт чужие циклы до `locks.code_update_wait_s` (1800 с), делает fast-forward и возвращает совместную блокировку. Если чужой цикл не закончился за это время, чекаут обновляется всё равно (PR уже слит на GitHub, отставший чекаут хуже) и пишется событие `code.update_not_exclusive`. Сам часовой проход после самослияния дорабатывает остальные продукты на старом коде в памяти, как и раньше. Ожидания — в `team.yaml`, секция `locks:` (`start_wait_s` 20 с — стартующий цикл пережидает короткую исключительную блокировку сторожа или ручного `flock data/cycle.lock …`).

Что ещё общее у параллельных циклов и чем закрыто: `data/billing.json` — свой замок `billing.json.lock`; `data/external-critic/seen.json` — замок `seen.json.lock` и атомарная запись (до F17 писался без замка); токены X — свой замок в `publish.py`; `data/cron.log` — оба входа дописывают в режиме append, строка лога пишется одним вызовом, в формате есть pid процесса (`INFO [12345] team.cycle: …`), чтобы различать строки параллельных циклов, а с 21.11 и метка дорожки для строк параллельных прогонов одного цикла (`INFO [12345 review-T-0042] team.cycle: …`; строка основного потока выглядит как раньше, сторож читает те же первые 19 символов); подробный лог цикла — `data/runs/<slug>/<cycle>/cycle.log` (метка дорожки — `INFO [exec-developer] team.cycle: …`); порт плейтеста выбирается непосредственно перед запуском сервера, а не до установки и сборки, под замком процесса, и выданный порт 180 с не выдаётся второму плейтесту того же цикла (`playtest.free_port`); копия состояния для канарейки снимается под замком канареечного продукта (ждёт его цикл до `locks.canary_state_wait_s`). Лимиты подписки Claude общие и замком не делятся: параллельные циклы расходуют окно быстрее, остановку при исчерпании делает `billing.paused` перед каждым прогоном роли. `backup-state.sh` замков не берёт, как и раньше.

**Параллельные дорожки внутри цикла** (решение владельца 21.11: «отсутствие параллельной работы — огромный блокер»; трения F21 и F29 запуска ai-battles; `team/lanes.py`, `team/cycle.py`, `team/gitops.py`). Замеры на первой игре, цикл 21.11 14:07 UTC: ревью 13 минут (один прогон tester — 376 с), затем game-designer 498 с, и только после этого developer получил задачу P0 — 22 минуты ожидания при загрузке сервера меньше 1 на 4 ядрах и 6,6 ГБ свободной памяти. Причин было две. Первая: фазы и прогоны внутри фаз шли строго по очереди, даже у разных ролей. Вторая: у репозитория продукта было одно рабочее дерево (`data/repos/<slug>`), в котором developer и designer по очереди переключали ветку `task/<id>`. Замки из предыдущего абзаца разводят **продукты**; этот абзац — про потоки **внутри цикла одного продукта**.

*Дорожка* — поток, который делает работу целиком: готовит, запускает роль (прогон — подпроцесс `claude -p`, потока достаточно), применяет результат. Ревью каждой выпущенной задачи — дорожка; каждое место из `cycle.execute_slots` — дорожка, в которой задачи этого места идут одна за другой; основной поток цикла ведёт collect, triage, measure, geo, voice, digest. Фаза review запускает дорожки ревью и возвращается; triage идёт рядом с ними; фаза execute запускает дорожки мест и ждёт все дорожки цикла (ревью тоже). Если фаза execute в цикле не выполнялась или цикл остановлен STOP-файлом, дорожки дожидаются в конце `Cycle.run`: к итоговой строке цикла все результаты применены.

| Что | Одновременно | По очереди |
|---|---|---|
| ревью выпущенных задач (reviewer, tester) | друг с другом, с triage (PO), с дорожками execute | — |
| роли со своей рабочей папкой (game-designer, analyst, marketer, tester с нагрузочной задачей) | с любыми другими ролями | задачи одной роли между собой |
| роли репозитория (developer, designer) | друг с другом — у каждой задачи свой чекаут | задачи одной роли между собой (по умолчанию) |
| слияние в базовую ветку, push и деплой после него | — | один критический участок на продукт (замок репозитория): последний выкаченный коммит — всегда последний слитый |
| деплой и игра на живом хосте | игры на живом хосте между собой; локальные серверы плейтеста на свободных портах — без ограничений | деплой ждёт идущие игры на живом хосте и идёт один; пока деплой ждёт или идёт, новая игра на живом хосте не начинается |
| collect, measure, geo, voice, digest | — | как раньше, в основном потоке |

Кого берёт execute, не изменилось: тот же порядок кандидатов (сначала `in_progress`, затем приоритет, затем возраст) и те же проверки; дорожка места — это тело прежнего цикла выбора для одного места. Отличие одно, и оно — цель изменения: задача, которую ревью этого же цикла вернуло автору, раньше занимала место своей роли первой, а теперь ревью ещё идёт, когда места заняты. Поэтому после того, как все дорожки закончились, execute делает ещё проход (до `EXECUTE_WAVES_MAX` = 3): запускает то, что стало возможным за этот цикл и чьё место свободно, — задачу, возвращённую ревью, и задачу, чью зависимость `depends_on` закрыла соседняя дорожка. Триаж PO видит вердикты ревью этого цикла в следующем цикле.

Сколько работает одновременно, решает счётчик `RunGate`: не больше `max_runs` дорожек вместе с прогоном основного потока (PO); из них не больше `review_max_runs` — ревью, чтобы для исполнения всегда оставалось место; освободившееся место получает сначала основной поток, затем дорожка execute, затем ревью. Дорожка держит место от начала до конца: клон, `npm ci`, сборка и unit-тесты, которые она делает вокруг прогона, нагружают сервер так же, как сам прогон. Настройки — `cycle.parallel` в `team.yaml`, product.yaml переопределяет по ключам (`cycle: {parallel: {...}}`):

```yaml
cycle:
  parallel:
    enabled: true            # false — строго последовательный цикл, как до 21.11 (ни одного потока; `parallel: false` — краткая запись)
    max_runs: 3              # дорожек одновременно внутри цикла одного продукта (1…8)
    review_max_runs: 2       # из них ревью; по умолчанию max_runs − 1, не меньше 1
    overlap_roles: []        # роли, чьи несколько мест (execute_slots.<роль> > 1) работают одновременно; пусто — задачи одной роли идут по очереди
    max_merge_conflicts: 2   # конфликтов слияния подряд на одной задаче до блокировки с вопросом PO
    worktree_keep_h: 72      # сколько часов хранить чекаут задачи в blocked / deferred / waiting_owner (ветка остаётся всегда)
    workdir_keep_h: 24       # сколько часов каталог завершённого цикла хранит клоны своих ревью и плейтестов (журналы остаются всегда)
```

Неверное значение пишется в лог уровнем WARNING и заменяется значением по умолчанию — опечатка не останавливает цикл. `team status` показывает строку `lanes:` с действующими значениями; итоговая строка цикла в логе дополнена числом дорожек и наибольшим числом одновременно работавших (`…, 4 lane(s), up to 3 at once`), `run.json` каждого прогона несёт поле `lane`.

*Один чекаут на задачу.* Роль репозитория работает не в клоне, а в `git worktree` своей задачи: `data/work/<slug>/wt/<id задачи>` на ветке `task/<id>` (`gitops.start_task_worktree`: новая ветка от свежей базовой либо ветка прошлой попытки со слитой в неё базовой, по тем же правилам, что были у `start_task_branch`). Клон `data/repos/<slug>` всегда стоит на базовой ветке, в нём диспетчер делает слияния. Чекаут переживает остановку прогона по времени: служебный коммит `wip:` лежит в нём, следующий цикл продолжает там же, и то, что git игнорирует (`node_modules`, сборка), остаётся на месте; незакоммиченные остатки неудачного прогона при следующем старте по-прежнему сбрасываются. Чекаут удаляется вместе с веткой при слиянии; у задачи, закрытой иначе (`rejected`, `done`, `accepted`), и у задачи, простоявшей в `blocked` / `deferred` / `waiting_owner` дольше `worktree_keep_h`, его убирает уборка в начале фазы execute (`Cycle.sweep_worktrees`, события `worktree.created` / `worktree.removed`) — ветка и её коммиты при этом остаются, вернувшаяся задача получает новый чекаут этой ветки. Чекаут ревьюера только для чтения и копия для плейтеста не изменились. Цена: зависимости не общие между чекаутами — в новом чекауте роль ставит их заново (об этом сказано в промпте). У сервисного репозитория две роли могут одновременно поднять сервер каждая в своём чекауте, поэтому прогон developer и designer получает собственный порт: переменная окружения `TEAM_PORT` и строка в промпте («`PORT=<порт>` серверу, `BASE_URL=http://127.0.0.1:<порт>` тестам»); сама `PORT` в окружение не подставляется, чтобы молча не увести сервер с порта, который ждёт тестовая конфигурация репозитория.

*Рабочие каталоги циклов.* Ревью и плейтест работают в клонах, сделанных на один прогон: `data/work/<slug>/<цикл>/review-<задача>/tests-run` (здесь диспетчер запускает тесты, после `npm ci` остаётся `node_modules`), `review-<задача>/checkout` (чекаут только для чтения) и `playtest-<задача>/checkout` (отсюда стартует сервер). Диспетчер убирает их сам, в два приёма. (1) Как только прогон ревью закончился (`Cycle.drop_review_dirs` в `finally` дорожки, до записи вердикта): `tests-run` и чекаут ревью удаляются целиком, в чекауте плейтеста и нагрузочного теста удаляются все `node_modules`. Вердикту они не нужны: `apply_review` читает только ответ прогона, свидетельства тестера лежат в `products/<slug>/reviews/<задача>`. Остаются `server.log`, файлы, которые сервер записал в свой чекаут, и всё, что прогон положил рядом. (2) В начале фазы execute, рядом с `sweep_worktrees`, `Cycle.sweep_work_dirs` проходит каталоги циклов, в которых ничего не менялось дольше `cycle.parallel.workdir_keep_h` часов (24): удаляет в них `<метка>/checkout`, `<метка>/tests-run` и все `node_modules`, ставит отметку `.swept` и больше в каталог не заходит. Сам каталог с журналами (`server.log`, `deploy-*.log`) остаётся. Не трогаются каталог идущего цикла и `wt`, `deploy`, `onboarding`. Один проход работает не дольше двух минут, остаток ждёт следующего цикла; итог пишется строкой INFO и событием `workdir.swept` (сколько каталогов, сколько удалено, сколько мегабайт освободилось). Причина: 25.11 диск сервера команды (154 ГБ) заполнился за пять дней — 803 каталога `node_modules` в 226 каталогах циклов ai-battles, 1,1–1,5 ГБ на цикл; цикл упал с ENOSPC.

*Переход со старой раскладки.* Продукт, который в момент обновления был посреди задачи (ветка `task/<id>` выбрана прямо в клоне, на ней может лежать `wip:`-коммит), продолжает без ручных действий: при первом же старте задачи репозитория `gitops.park_on_base` возвращает клон на базовую ветку (строка WARNING в логе; ветка и её коммиты остаются, незакоммиченные остатки сбрасываются, как их сбрасывал и прежний код), задача получает чекаут своей ветки, и блок CONTINUATION находит `wip:`-коммит там. Так же клон приводится в порядок после слияния, прерванного убитым процессом.

*Конфликт слияния.* Раньше конфликт при выпуске был невозможен: задачи шли по очереди, каждая стартовала от свежей базовой ветки. Теперь developer и designer могут изменить одни и те же строки. Тогда `gitops.merge_and_push` отменяет слияние (базовая ветка, ветка задачи и её чекаут остаются как были) и поднимает `MergeConflict`; цикл не падает. Задача возвращается автору в `in_progress` с полем `merge_conflict` (файлы, строки `CONFLICT` от git, что базовая ветка изменила в этих файлах), пишутся событие `merge.conflict` и одно наблюдение класса `environment_error` для PO. При следующем старте диспетчер пробует влить базовую ветку в ветку задачи обычным слиянием; если оно конфликтует, слияние отменяется и ветка остаётся без базовой (с 21.11, трение F39: прежний запасной путь `merge -X ours` молча выбрасывал сторону базовой ветки, после чего ветка сливалась чисто и main терял выпущенную работу других задач). Промпт получает блок `MERGE CONFLICT — RECONCILE FIRST, DO NOT REDO THE TASK` с текстом конфликта: автор сам вливает базовую ветку, разрешает конфликт так, чтобы работали оба изменения, прогоняет тесты и сообщает `done`. После `max_merge_conflicts` конфликтов подряд — `blocked` и вопрос PO (упорядочить задачи через `depends_on`, сузить одну или закрыть). Документы game-designer'а (он возвращает файлы целиком) коммитятся на ветку, начатую от того коммита базовой ветки, который роль читала, и сливаются как любая задача: чужая правка того же документа либо сливается с ними, либо даёт конфликт — тогда задача возвращается в `ready` и пишет документ заново на новой базе, ничего молча не перетирая.

*Общее состояние и чем оно закрыто* (инварианты записаны в начале `team/lanes.py`):

| Состояние | Чем закрыто |
|---|---|
| YAML-файлы задач, вопросов, наблюдений, ревью; `team.db` (события, расход, лизы, посты) | каждый пишущий метод `Store` — под `Store.lock` (повторно входимый): номер id берётся и записывается одним шагом; у каждого потока своё соединение SQLite. Участки «прочитал задачу — изменил — записал» там, где ту же задачу может тронуть другой поток (решения PO рядом с идущими ревью), обёрнуты в тот же замок |
| порядок применения результатов | результат применяется **по мере завершения прогона**, под замком хранилища, а не в фиксированном порядке после всех прогонов: дорожка чередует прогоны с записями (marketer → editor → marketer; developer → merge → деплой), и отложенное применение задержало бы слияния, деплой и лизы. История каждой задачи остаётся упорядоченной; номера наблюдений, вопросов и ревью, рождённых в разных дорожках, идут в порядке завершения прогонов |
| одна задача — одна дорожка | ревью не берёт задачу, чьё слияние или деплой ещё идёт в дорожке execute; execute не берёт задачу, которая на ревью (`Lanes.working` / `busy`) |
| клон репозитория: fetch, создание и удаление чекаутов, merge, push, деплой после merge, копирование клона для ревью и плейтеста (только само копирование) | замок репозитория цикла (`Cycle.repo_lock`); двух циклов одного продукта не бывает (`data/locks/product-<slug>.lock`), поэтому замка в памяти процесса достаточно |
| живой хост | замок «читатели — писатель» (`HostLock`): деплой — писатель, игра tester'а на живом хосте — читатель |
| дневной лимит продукта | `Cycle.role_run` резервирует лимит прогона до старта и снимает резерв, когда расход записан: потрачено + зарезервировано никогда не больше дневного лимита, сколько бы дорожек ни стартовало разом; прогон, которому не хватило, не запускается (`budget.stop` с полем `reserved`), задача остаётся в `ready` |
| `data/billing.json` | свой файловый замок на каждой записи (`billing.observe`), как и раньше; общий кредитный лимит между процессами резервом не делится |
| `data/cron.log`, `cycle.log` | запись строки атомарна (замок обработчика `logging`); метка дорожки в формате |
| порт плейтеста | замок процесса и удержание выданного порта |

Порядок замков один: место в счётчике → замок репозитория → замок хоста → замок хранилища или бюджета; под замком хранилища ничего не ждёт ни места, ни репозитория. Исключение в дорожке завершает только её: остальные дорабатывают, пишется `phase.error` с меткой дорожки, фаза не попадает в список выполненных фаз цикла (итоговая строка и `team status` остаются правдивыми).

Что **не** изменилось: шлюзы фаз, STOP-файл, `paused`, dry-run, `max_continuations`, постоянные направления, правило гипотез, пауза `review_after_min`, выбор задач. Отключение: `cycle.parallel.enabled: false` в `team.yaml` (или у одного продукта) — цикл снова строго последовательный, чекауты задач остаются. Вне этого изменения, следующий шаг: несколько мест одной роли одновременно по умолчанию (два developer'а) — механизм готов (`execute_slots.developer: 2` и `overlap_roles: [developer]`, покрыто тестом), но по умолчанию выключен; событийный планировщик вместо циклов.

**Правило гипотез** (владелец 07.11, `team/hypothesis.py`): задача типа `feature` от PO несёт гипотезу — кто, боль словами людей, доказательства, изменение, ожидаемый эффект, метрика, `min_sample` (сколько живых людей нужно, чтобы прочитать эффект), `read_on` (будущая дата) и оценка reach × pain × confidence × ease (1–5). Доказательство — хотя бы одно от живых людей: `voice:<дата>:P#`, наблюдение класса `feedback`/`voice` или внешняя ссылка на слова человека; персоны, внешний критик, ревьюер и метрики сами по себе не считаются. Без этого фича создаётся в `proposed`, а готовая фича без гипотезы перед стартом возвращается в `proposed`; PO поднимает её через `promote_tasks`, когда появилось доказательство. Когда наступает `read_on` принятой фичи, диспетчер кладёт PO одно наблюдение `hypothesis_readout`: подтвердилась / опровергнута / мало людей. Вне правила — дефекты, задачи качества, контент, маркетинг, задачи аналитика, задачи владельца и ретро.

**Правило качества** (владелец 08.11): разработчик не простаивает, пока что-то сломано или измеримо хуже, чем должно быть. Тип `defect` — сломано или неправда; тип `quality` — то же самое, сделанное лучше без нового обещания: скорость, упавшие проверки SEO/GEO, вёрстка на 375 px, доступность, понятность того, что уже есть, полнота данных. В `problem` — источник (упавшая проверка, провал ревью, `ux_friction` персоны, находка критика, URL и что видно). Если у разработчика нет задач, диспетчер будит PO не чаще раза в `cycle.dev_idle_po_every_h` (12 ч, владелец 09.11) с просьбой поставить 1–2 такие задачи; новая страница, раздел или возможность — это `feature` под правилом гипотез.

Правило PO (T-0042): задача, критерии которой выполнимы без правки репозитория (ежедневная проверка данных, «Check:»), — задача analyst (или тип `check`) либо называет файл для правки; developer-задача без ожидаемого коммита — дефект задачи (F-0104, F-0107, F-0109, F-0110, F-0113).

Правило PO (T-0064): перед постановкой задачи PO сверяет имена полей и объектов в критериях с ограничениями самой задачи (например, «без переименования» против «объект `sample`»); при конфликте в тексте задачи сказано, что главнее (пример: T-0077, F-0134; также F-0132).

Правило PO (T-0159): критерии приёмки проверяемы на живом сайте либо в репозитории с `repo_only: true`; нет критериев «`built_at` сайта против времени merge-коммита» и «0 изменений файлов при второй пересборке» (это тест `repo_only`), и нет формулировки «каждая страница /go/, связанная с X» без перечня типов страниц (F-0225, F-0226, F-0197).

Правило PO (T-0073): задача dev.to называет canonical — датированную страницу `/d/<date>/` или страницу находки с `?src=devto`, никогда корень сайта (повтор даёт 422); открытую задачу с корнем в приёмке (T-0052) PO исправляет сам, вопрос владельцу не открывается.

Правило triage: PO видит `not_before` каждой задачи бэклога; предложенная задача с тем же названием или с той же парой «роль + `not_before`», что у открытой, не создаётся (событие `task.duplicate_skipped`, строка в дайджесте PO). PO закрывает лишние задачи через `close_tasks` → `rejected`.

Правило «новый инструмент пробуется в день появления» (владелец 03.11): новый канал в `product.yaml`, новый флаг инструмента, новый файл данных — PO ставит первую настоящую пробу в ближайший цикл (`not_before` = сейчас), а не в план на следующие дни; результат пробы идёт в план. Инструмент, пролежавший сутки без пробы, — дефект PO.

Опыт читателя — цель, а не побочная проверка (решение владельца 32, 04.11: «персоны на Opus, фокус на user experience, интересе и пользе; нельзя, чтобы только внешний критик работал на это»): персоны запускаются дважды в день на продукт по 2 сценария в ротации. Расписание — по времени, как у SEO-проверки и голоса пользователя: `cycle.persona_every_h` (12 ч; 0 — выключено), отметка последнего прогона — `products/<slug>/personas-last.json` (когда начат, какие сценарии, сколько вернули результат, с какого сценария продолжит ротация; `team/ux.py`). Отметка пишется до запуска ролей, поэтому цикл, убитый посреди прогона, не запускает персон заново каждый час; прогон без единого результата повторяется через `cycle.persona_retry_h` (3 ч), а не через весь период. Число циклов в расписании не участвует (до 22.11 условие считало циклы через `Store.cycles()`, который отдаёт не больше 50 строк, и после 50-го цикла продукта персоны не запускались: с 04.11 по 22.11 — ни на одном продукте). Прежний ключ `persona_every_n_cycles` читается как часы с предупреждением в логе. Простой виден в проверке автономности: C18 «прогоны персон по продуктам» — WARN, если у продукта со сценариями и открытым гейтом `persona` нет прогона с результатом дольше 26 ч. Оценки персон копятся, PO видит средние и желания и при интересе или пользе ≤ 3 ставит хотя бы одну задачу за цикл на интерес и пользу раньше внутренних улучшений. Находки персон `ux_friction`/`value_gap` весят как находки внешнего критика. Ни персоны, ни критик не спрос: первым остаются счётчик людей и слова живых людей.

Заместитель владельца (`deputy`, мандат `DEPUTY.md` — защищённый путь): вопрос владельцу, открытый дольше `deputy.after_h`, получает ответ по мандату — `decided` (консервативный выбор внутри VISION), `unavailable` (секреты, деньги, аккаунты, каналы, цели VISION: «недоступно до возвращения, действуй без этого или закрой задачу») или `info`; задача выходит из `waiting_owner`. Введено 03.11 на неделю отъезда владельца (решение 27).

Правило повтора: если developer вернул `partial` и его friction (наборы `kind`) пересекается с предыдущей попыткой (общий вид `kind`; `environment` не считается, если есть другие виды; полное равенство наборов не требуется) (или совпал summary / текст friction), задача сразу `blocked`, PO получает вопрос; третий почасовой запуск не стартует (T-0024).

**Промпт PO** (владелец 26.11, срез 1 большой доработки; `team/prompts.py` `po_prompt`, `finished_brief`). Замер на ai-battles за 24–26.11: запуск PO стоил 3,71 доллара (медиана), 45 % расхода продукта; 89 % промпта занимал раздел `# BACKLOG`, из него 88 % — полные тексты 119 задач, по которым работа сделана. Настройка `cycle.po_prompt` (team.yaml, `product.yaml` переопределяет по ключам, оба ключа по умолчанию выключены): `compact_finished` — задача в `accepted`, `released`, `measured` идёт карточкой (`id`, `title`, `state`, `type`, `role`, `goal`, `links`, `accepted_at`, `outcome` — одна строка итога последнего результата до 200 знаков), незавершённые идут полным текстом, ни одна задача из раздела не пропадает; `stable_first` — промпт начинается с VISION, а номер цикла, расход и предел готовых задач стоят в конце, в разделе `# THIS CYCLE`. Откат: убрать блок `po_prompt` из `product.yaml`.

**Нехватка данных** (владелец 26.11, срез 2а; `Cycle.context_result`, `ask_for_context`, `task_answers`, `prompts.answers_block`). Роль, которой не хватает данных для задачи, возвращает `status: needs_context` и список `missing` (до пяти пунктов); геймдизайнер возвращает `files: []` и `missing`. Настройка `cycle.escalation.needs_context` (по умолчанию выключена): список превращается в один вопрос PO, задача уходит в `blocked` с `blocked_by` и ждёт ответа; результат записан как `needs_context`, в счётчик неудач застрявшей цели и в `attempts` не идёт. PO отвечает из VISION и решений владельца либо кладёт пункт в `owner_questions` с `task_id` (задача ждёт в `waiting_owner`). Ответы PO и владельца приходят роли в промпт разделом `# ANSWERS TO THIS TASK'S QUESTIONS`. При выключенной настройке `needs_context` обрабатывается как прежний `blocked` с `question`.

**Возврат с проверки** (владелец 26.11, срез 2б; `Cycle.return_from_review`, `retry_review`). Настройка `cycle.escalation.review_return` (по умолчанию выключена; действует там, где третий вердикт без доказательства блокирует задачу, то есть у профиля `game`): третий `inconclusive` возвращает ту же задачу исполнителю (`in_progress`) с причиной из фиксированного списка `team/play.py INCONCLUSIVE_REASONS` и указанием, что сделать (`REVIEW_RETURN_TODO`); вопрос PO и новая задача не создаются, событие `review.returned`. Причины среды (`lock_timeout`, `server_not_started`, `test_tooling`, упавший запуск ревью) исполнителю не возвращаются: ревью повторяется, до двух раз на задачу (`review.retry`). После двух возвратов действует прежнее правило: `blocked` и вопрос PO.

**Дубли задач** (владелец 26.11, срез 3; `prompts.closed_block`, `cycle.closed_twin`). Замер на ai-battles за 20–26.11: проверка открытых задач (`duplicate_task`) отсекла 4 предложения за пять дней, повторных запусков одной задачи нет (`working`, `store.lock`, набор `_taken` фазы исполнения). Настройка `cycle.duplicates` (по умолчанию выключена): `closed_list` — раздел `# CLOSED TASKS` в промпте PO, строка на задачу, закрытую за 7 дней (80 новейших): номер, состояние, название, причина закрытия; `closed_check` — название предложенной задачи сверяется с закрытыми за 14 дней: сделанная работа (`done`, `accepted`, `measured`) повторно не заводится, преемник отклонённой задачи создаётся и получает `continues` на неё. Не сверяются задачи с `not_before`, задачи постоянных направлений, задачи другой роли и те, что сами называют закрытую в `continues`.

**Сторожа запуска** (владелец 26.11, срез 4; `team/runner.py LoopGuard`, `Cycle.cost_guard_cap`). Настройка `cycle.guards` (по умолчанию выключена). `loop`: запуск, который `loop_repeats` (5) раз подряд сделал один и тот же вызов инструмента с тем же входом и тем же выходом, снимается; ожидание фоновой команды (тот же вызов, выход меняется) петлёй не считается; вызовы роли и каждого субагента считаются отдельно. Снятый запуск разработчика или художника продолжается в следующем цикле, как после предела времени. `cost`: предел расхода запуска не выше `cost_factor` (8) медиан расхода роли за `cost_days` (7) дней, не ниже `cost_floor_usd` (1 доллар), и только если у роли есть `cost_min_runs` (20) запусков; запуск останавливает сам CLI по `--max-budget-usd`. Оба случая пишутся в регистр трудностей видами `run_loop` и `run_cost`. Предел времени, сторож тишины и `stall-watch.sh` не тронуты.

**Видимое изменение** (владелец 26.11, срез 5; `Cycle.review_first`, `hold_for_review`, `merge_task`; полное описание и схема предпросмотра: `docs/review-before-deploy.md`). PO помечает задачу `visible`, `redesign`, `new_function`. Настройка `cycle.visible` (по умолчанию выключена): `review_before_merge` — задача с `visible` после отчёта исполнителя не сливается, а идёт в `review` с пометкой `pre_merge`; ревью играет её коммит на локально поднятом сервере, «принято» сливает ветку и переводит задачу в `accepted`, дальше обычная выкладка; «не принято» возвращает исполнителю. `redesign_gate` — задача с `redesign` без `new_function` ждёт в `proposed` слова владельца (принцип «редизайн делаем только при новом функционале»). Порядок видимой задачи: `in_progress → review → accepted → выкладка → measured`; невидимые идут как раньше.

**Непрерывная работа мест** (владелец 25.11: «кто дал замок и сколько было простоев из-за него? если у нас так простои постоянно, то, наверное, надо что-то менять»; `team/flow.py`, `team/cycle.py`, `team/cli.py`). Замеры на ai-battles за 21–25.11 (таблицы `cycles`, `events`, файлы `run.json`): места исполнителей работали 18 % времени четырёх слотов запусков, при этом всё время ждали 8–28 готовых задач. Из простоя 42 процентных пункта дало устройство цикла: 28 — место сделало свою задачу и ждало самого долгого запуска цикла (в 88 циклах из 211 цикл пять и более минут держал один последний запуск), 14 — пауза 5–10 минут между циклами (`cycle.every_min` считается от конца цикла, cron смотрит раз в 5 минут). Остальное с циклом не связано: 36 — для роли со свободным местом не было готовой задачи (очередь почти целиком у developer, у него 2 места), 4 — дневной лимит 24.11. Настройка `cycle.flow` (team.yaml, по умолчанию выключена; `product.yaml` `cycle: {flow: {...}}` переопределяет по ключам; сокращение `flow: true` включает оба пункта):

- `refill: true` — подпитка мест. В фазе execute место, закончившее задачу, берёт следующую пригодную, пока фазе меньше `refill_min` минут (по умолчанию 20). Бэклог для каждого выбора читается из хранилища заново, в обычном порядке (`in_progress` → приоритет → возраст): задача, которую ревью этого цикла вернуло автору, и задача, добавленная или отложенная оператором минуту назад, учитываются. `execute_slots` при этом значит «сколько мест роли работает одновременно», а не «сколько задач за цикл». Число дорожек не растёт: инварианты 1 и 3 «Параллельных дорожек» (не больше `max_runs` запусков разом, одна дорожка на роль вне `overlap_roles`) действуют как раньше. После `refill_min` новое не стартует, поэтому цикл не длиннее, чем его и так держит один долгий запуск. Исключение по замерам 24–25.11: в 23–29 % минут внутри цикла шли одни ревью (плейтесты по 25 минут в очереди за слотами запусков), а места исполнителей их ждали; пока ревью этого цикла идут или ждут слот, цикл всё равно занят, и подпитка остаётся открытой, но не дольше `refill_max_min` (60). Подпитка закрывается до конца цикла (событие `flow.refill_closed` с причиной), если запуск упал или не стартовал (дневной лимит, лимиты подписки, сбой CLI): следующая задача встретила бы то же, а её `attempts` сгорели бы зря.
- `chain: true` — цикл встык. `team cycle --due` после цикла, который довёл до конца хотя бы одну задачу, сразу запускает следующий цикл продукта в том же процессе, пока есть пригодные к старту задачи (`Cycle.work_waiting`), не больше `chain_max` циклов подряд (по умолчанию 6). Между циклами процесс на `chain_pause_s` секунд (5) отпускает все замки: скрипт оператора, ждущий `flock data/locks/product-<slug>.lock`, получает замок в этом окне, а следующий цикл ждёт его до `chain_lock_wait_s` (120 с); обновление кода получает свою очередь у ворот. Цепочка кончается, если изменился чекаут диспетчера (`git rev-parse HEAD`: процесс держит в памяти старый код), у ворот ждёт обновление кода, появился STOP или пауза, цикл ничего не довёл до конца, или идентификатор цикла (минута UTC) совпал с предыдущим — тогда решают cron и `cycle.every_min`, как раньше.
- Предохранители общие для обоих пунктов (`flow.allowed`): дополнительная работа не стартует, пока команда идёт на купленных кредитах (`using_credits` в `data/billing.json`; `on_credits: true` снимает запрет), и пока недельное окно подписки выше `max_utilization` (по умолчанию 1.0 — без потолка). Дневной лимит продукта проверяет `Cycle.role_run`, как всегда. `team status <slug>` печатает строку `flow: …` и причину, если подпитка и цепочка сейчас выключены предохранителем. Итог цикла в журнале: `…, N task(s) executed, M of them by refill`.

**Записи извне во время цикла** (25.11; `team/store.py` `StoreLock`, `team/cli.py`). До 25.11 единственной защитой хранилища от второго процесса был замок продукта: номера задач и наблюдений берутся как «наибольший файл + 1», и два процесса могли взять один номер, поэтому оператор запускал `team obs` и `team task new` под `flock data/locks/product-<slug>.lock` и ждал конца цикла, до 45 минут. Теперь `Store.lock` — это и замок потоков, и `flock` на `products/<slug>/store.lock`: каждая запись и каждая короткая секция «прочитать-изменить-записать» цикла исключает и другие процессы. Цикл держит его миллисекунды (инварианты 4 и 8 дорожек: никогда через запуск модели, слот или замок репозитория), поэтому `team obs`, `team task new`, `team task move`, `team ask`, `team answer` запускаются без замка продукта в любой момент. Одно исключение — `team task move` задачи, над которой прямо сейчас работает дорожка идущего цикла (у дорожки своя копия задачи, она запишет её поверх): цикл отмечает такие задачи в таблице `working` хранилища, команда отвечает кодом 75 и именем дорожки либо ждёт с `--wait-s N`; место, прежде чем начать задачу, ставит отметку и читает задачу заново, так что перенос, сделанный секундой раньше, оно видит и задачу не берёт. Правка файлов продукта вне хранилища (`VISION.md`, `product.yaml`) внешними скриптами по-прежнему идёт под замком продукта: VISION целиком входит в промпт каждого запуска PO, исполнителей и ревью, `product.yaml` цикл читает при старте, и правка посреди цикла дала бы запускам одного цикла разные версии. Ждать приходится до конца текущего цикла; с `chain` окно для такого скрипта открывается между циклами цепочки.

**Выкладка пачкой** (владелец 25.11: «чтобы выкладка шла пачкой, раз в цикл, а не после каждой задачи»; `team/cycle.py` `deploy_batch`, `team/config.py`). Замер на ai-battles за 25.11: 52 выкладки игры диспетчером (67 вместе с ручными), по одной после каждого слияния; каждая от полуминуты до пяти минут держит живой хост исключительно и обрывает бои живых игроков; 17 выкладок ждали плейтесты, суммарно 124 минуты, с замком репозитория в руках. Настройка продукта `deploy: {batch: true}` (по умолчанию выключена, только для `deploy.mode: service`):

- Слияния идут как раньше, по мере готовности задач. После слияния задача `released` получает поле `deploy_pending` (время слияния) и событие `deploy.queued`; на хост ничего не идёт.
- Хост переключается один раз за цикл: в конце фазы execute, когда все дорожки закончили, на голову базовой ветки, под замком репозитория. Событие `deploy.ok` пачки: субъект — цикл, в деталях `batch`, `tasks`, `waited_s` (сколько ждало самое старое слияние), `host_wait_s` (сколько ждали плейтесты), `why`.
- Задача считается выкаченной (`deployed_sha`, `deployed_at`) только после пачки. Ревью и плейтест задачи с `deploy_pending` не стартуют: тестер играет на живом хосте.
- Предел ожидания `deploy.batch_max_wait_min` (45): если самое старое слияние ждёт дольше, пачка уходит сразу — при очередном слиянии или по таймеру цикла, не дожидаясь конца фазы.
- Невыкаченное не теряется: фаза review следующего цикла (в цепочке или после падения процесса) начинается с пачки для оставшихся `deploy_pending`.
- Неудача пачки. Сбой хоста или доставки (push, ssh, nginx, тайм-аут) никого не винит: задачи ждут, следующая пачка пробует снова, до трёх раз, PO получает одно наблюдение `environment_error`. Иная неудача (сборка, проверка здоровья) или исчерпанные попытки: прежний путь по одной задаче — собственный коммит слияния каждой ждущей задачи выкладывается в порядке слияний; прошедшие становятся выкаченными, не прошедшая уходит в `blocked` с вопросом PO, как без пачки. Скрипт не переключает хост до проверки здоровья, поэтому живым остаётся последний удачный выпуск.
- `team deploy <slug> --sha S` и `--rollback` работают как раньше; следующая пачка выложит голову ветки (или получит «уже выложено»).
- Инвариант 5 дорожек в новой формулировке: в момент выкладки на хост идёт последний слитый коммит, он содержит все слияния с прошлой выкладки; между выкладками хост стоит на более раннем слиянии.

Места в execute: `cycle.execute_slots` — по одному месту на роль за цикл (developer 1 · marketer 1 · analyst 1; product.yaml может переопределить), чтобы ежедневный пост не голодал за задачами разработчика (03.11). С `cycle.flow.refill` (25.11, «Непрерывная работа мест» выше) число мест значит «работают одновременно»: освободившееся место берёт следующую задачу в том же цикле. С 21.11 места работают одновременно, каждое в своей дорожке («Параллельные дорожки» выше); общее место `*` (`max_execute_per_cycle` без `execute_slots`) — одна дорожка, задачи в ней идут по очереди. Маркетинговая задача без записанной публикации ревьюером не принимается — `blocked` и вопрос PO; исключение — план-задача (`plan: true`), её приёмка — наличие `marketing-plan.md`.

Маркетинг по плану (03.11, оценка сессии каналов: роль была реактивна — одна задача = один пост, без плана, памяти и обратной связи): `products/<slug>/marketing-plan.md` — неделя по каналам; PO создаёт план-задачу, когда плана нет или он старше 7 дней, и режет слоты плана на пост-задачи с `not_before`; маркетолог в каждом прогоне видит опубликованное за 7 дней, переходы по `?src=` за 14 дней с вердиктом по каналу и слова людей; `metrics/latest.md` показывает строку `Visits by ?src=`.

Лимиты по каналам (владелец 10.11, данные 02–10.11 по всем сайтам: X ≈ 23 человека с 24 постов, Bluesky 8/46, Telegram 3/46, Mastodon 3/11, Threads 1/16, dev.to 0/4): `publish.channel_caps` в `team.yaml`, на продукт — X 1 в день, Bluesky и Telegram 2 за 7 дней, Mastodon, Threads и dev.to 1 за 7 дней. `team-publish` отказывает сверх лимита; PO и маркетолог видят лимиты и причину в промпте и не ставят слоты сверх них. В метриках браузерный источник, открывший за день только `/go/` (без страницы, файла сайта и внешнего referer), считается `unknown`, не человеком; число таких — `go_only_excluded`. С 18.11 так же считается источник, загрузивший файлы сайта (иконку, CSS) без единой страницы (`no_page_excluded`). «Заинтересованным» (engaged) не считается источник, который открыл одну внутреннюю страницу без referer и без `?src=` и больше ничего (`drive_by_not_engaged`): так выглядят сети прокси-скрейперов, у agentsmd 13–16.11 их было 1 400–3 800 в день. Человек приходит по ссылке, открывает главную или вторую страницу.

Фаза execute, «сделано, но ничего не закоммичено» (T-0038): первый такой результат возвращает задачу в `ready`, а в заметке перехода (её читает `friction.py`, вид `no_commit`) лежат резюме developer и начало `self_check`. Второй подряд — задача сразу `blocked`, PO получает вопрос «переформулировать, разбить или закрыть»; третий запуск не стартует. Гварды результата (03.11 вечер): `partial`, повторивший предыдущий (тот же итог или те же трудности), блокирует задачу с вопросом PO — не крутится дальше; результат-заглушка аналитика (короче 120 знаков или «дубликат вызова / см. предыдущий отчёт») не закрывает задачу — `blocked` + вопрос PO. Застрявшая цель (владелец 11.11, Luz T-0117 → T-0130: семь запусков спрашивали один и тот же файл OMIE, а общий файл с колонкой Португалии лежал рядом). Неудачи считаются по цепочке задач одной цели: предшественники — из поля `continues` (PO ставит его, когда пересоздаёт цель) или из заголовка/проблемы («replaces T-…», «retry of …», «instead of …»). Неудача — результат `partial`/`blocked`/`error` или запись «committed nothing». При `replan.threshold` (3) неудачах developer не запускается: задача `blocked`, `replan.state = asked`, и в промпте PO появляется блок STUCK GOALS со списком испробованного. PO отвечает в `replans`: диагноз и ровно 3 альтернативы, отличные по сути от испробованного, хотя бы одна меняет источник данных или постановку; иначе ответ не принимается. Диспетчер создаёт 3 пробы — задачи developer с `probe_of`, бюджет `replan.probe_budget_usd`, без слияния кода; проба «работает», если `done` и все пункты `self_check` выполнены со свидетельством. Работающая проба → исходная задача `rejected` (`replan.state = done`), PO получает вопрос «создай одну задачу реализации с `continues`»; счётчик после завершённого перепланирования начинается заново. Ни одна не сработала, или цепочка застряла второй раз после перепланирования → вопрос владельцу (сначала отвечает заместитель); ответ дописывается в scope задачи, повторного автоматического перепланирования нет. Задача с заголовком `[retro]` (правка фреймворка) эскалируется так же после одного перепланирования, даже если её пересоздали под новым id с тем же заголовком: ровно один вопрос владельцу, он называет файл, который нужно поправить вручную (T-0186). `team/replan.py`.

Правило `depends_on` (T-0027): необязательное поле задачи — список id; готовая задача не запускается, пока каждая зависимость не в состоянии `accepted`/`measured`/`done` с непустым (не заглушечным: ≥ 120 символов, без «дубликат вызова» и т. п.) последним результатом; неизвестный id = не выполнено. Правило повторного partial: второй подряд `partial` (или `partial` после `blocked`) с общим видом трудности (`environment` игнорируется, если есть другие виды) либо с тем же резюме блокирует задачу и задаёт вопрос PO; проверка выполняется до проверки «ничего не закоммичено», поэтому partial без коммитов тоже считается; третий запуск не стартует.

Правило execute: готовая задача, в названии которой есть дата `ДД.ММ` позже сегодняшней (UTC), но нет `not_before`, не запускается; диспетчер пишет наблюдение для PO (поставить `not_before`). Задача, дважды заблокированная одним и тем же вопросом, не перезапускается автоматическим (не владельческим) ответом без `not_before`; событие `task.restart_suppressed`.

С 22.11 (владелец, разбор дня ai-battles) третий `inconclusive` у продукта профиля `game` не принимает задачу, а переводит её в `blocked` (`blocked_by: review`) с вопросом PO «проверить не удалось, результата никто не видел»; `product.yaml: review: {inconclusive: accept | ask}` задаёт правило явно, без ключа: `ask` для `game`, `accept` для остальных профилей (`Cycle.inconclusive_policy`). Копия репозитория для тестера собирается (`repo.build_cmd`) и при проверке по живому адресу (`playtest.start`). Правка game-designer, которая меняет файл данных (`.json`, `.yaml`, `.yml`, `.csv`), перед слиянием проходит тесты репозитория (`repo.test_cmd`); при красных тестах не сливается, задача блокируется с вопросом PO (`Cycle.exec_game_designer`, событие `design.tests_failed`). Ниже прежнее описание правила. Правило неопределённого ревью (в коде с пилота, описано при сверке 21.11; `Cycle.review_task`, `team/cycle.py`): вердикт `inconclusive` оставляет задачу в `released` и увеличивает счётчик `review_inconclusive`; на третьем таком вердикте задача переходит в `accepted` с заметкой «inconclusive 3×: accepted without external proof» — принята без наблюдения результата. Счётчик не сбрасывается между попытками. Так у ai-battles 20.11 принята T-0005 (макеты в `docs/`, которые tester не мог открыть), а зависимые задачи ждали три цикла (трение F16). Исключение — маркетинговая задача без записанной публикации: она уходит в `blocked` с вопросом PO. Отдельный счётчик: прогон ревью, который сам упал три раза (нет структурированного ответа), переводит задачу в `blocked`.

Состояния задачи: `proposed → ready → claimed → in_progress → review/released → accepted → measured → done`;
боковые `blocked`, `waiting_owner`, `rejected`, `deferred`. Каждый переход — в `history[]` задачи.

Таймаут и сбой прогона (в коде с пилота, описано при сверке 21.11, изменено 21.11 решением владельца; `team/runner.py`, `team/cycle.py`). Прогон роли ограничен жёстким лимитом `timeout_s` (по умолчанию `claude.timeout_s` = 1500 с) и сторожем `inactivity_s` (300 с без единой строки вывода); с 21.11 оба числа задаются на роль и на продукт (следующий абзац). По истечении диспетчер убивает только процесс `claude` (`proc.kill()`): процессы, которые роль запустила через `Bash` (сервер, Playwright), группой не убиваются и могут пережить прогон (трение F22 ai-battles: сервер игры на порту 3101 прожил около 10 часов). Стоимость такого прогона неизвестна и записывается как `budget.unknown_cost_reserve_usd` = $0.50. Прогон developer и designer, остановленный лимитом времени или сторожем, — не сбой, а продолжение (следующий абзац). Любой другой неудачный прогон developer, designer, game-designer и tester (и остановленный лимитом у game-designer и tester) даёт результат `error` и счётчик `attempts`: до трёх неудачных прогонов задача возвращается в `ready`, на третьем — `blocked` без вопроса PO; счётчик общий с «ничего не закоммичено» и не сбрасывается. Задачи marketer и analyst возвращаются в `ready` без счётчика. После такого сбоя (не остановки по времени) незакоммиченная работа ветки по-прежнему теряется при следующем старте (`gitops.start_task_worktree`: `reset --hard`, `clean -fd` в чекауте задачи), коммиты `task/<id>` сохраняются.

**Бюджет времени, продолжение и профиль прогона** (решение владельца 21.11: задача, не законченная за цикл, должна продолжаться; времени нужно давать больше, потому что задачи будут усложняться; и нужно видеть, сколько времени уходит и не гоняет ли роль лишние git и проверки; трения F23 и F30 запуска ai-battles: прогон разработчика шесть раз за день упёрся в 1500 с, незакоммиченную работу оператор коммитил руками; ручной разбор одного прогона — из 1252 с в инструментах 1241 с заняли 20 запусков Playwright на одной спеке, git — 0 с). Четыре части.

1. *Бюджет на роль и на продукт* (`config.run_limits`). Слои, выигрывает последний: `claude.timeout_s` / `claude.inactivity_s` (общие) → `claude.roles.<роль>` (team.yaml) → `claude.roles_by_repo_kind.<repo.kind>.<роль>` (team.yaml; из коробки одно значение: developer сервисного репозитория — 2700 с) → `roles.<роль>` в product.yaml. Жёсткий потолок — константа `RUN_TIMEOUT_CEILING_S` = 3600 с: значение выше обрезается с WARNING (и в `Runner.run`, если его зовут в обход). Сторож не длиннее лимита. Неверное значение (не положительное число) пропускается с WARNING, действует слой ниже. Действующий лимит и слой, из которого он взят, пишутся в лог при старте прогона и в `run.json` (`limits`). Без новых ключей все роли, кроме developer сервисного репозитория, работают с прежними 1500 / 300 с.
2. *Роль знает свой бюджет.* В промпте developer и designer — блок `TIME BUDGET OF THIS RUN`: минуты прогона, время старта и правило «когда использовано около двух третей — не начинать новое, убедиться, что дерево собирается, закоммитить и вернуть `partial` со списком оставшегося». `partial` обрабатывается как раньше (переход `partial — continues next cycle`, гвард повтора); новое — если роль вернула `partial` и оставила незакоммиченные файлы, диспетчер сохраняет их коммитом `wip: <id> — partial result, continues next cycle`, а не теряет при следующем старте.
3. *Продолжение вместо перезапуска* (`Cycle.continue_interrupted`, `gitops.save_wip`). Прогон developer или designer убит лимитом или сторожем → диспетчер коммитит всё рабочее дерево чекаута задачи (`data/work/<slug>/wt/<id>`, «Параллельные дорожки» выше; чекаут сохраняется до слияния, продолжение идёт в нём же) на `task/<id>` служебным коммитом `wip: <id> — run stopped by the time limit, continues next cycle` (без хуков; только на ветке задачи — если чекаут стоит на другой ветке, коммит не делается, событие `run.wip_failed`, прогон считается обычным сбоем; ветка никуда не пушится, в base ничего не попадает, деплоя нет), пишет событие `run.wip_saved` (число файлов, коммит, причина) и результат задачи со статусом `interrupted` (не считается неудачей для счётчика застрявшей цели и не увеличивает `attempts`). Задача остаётся `in_progress`, счётчик `continuations` растёт; следующий цикл берёт её первой, и промпт получает блок `CONTINUATION — DO NOT START OVER`: коммит wip и его `--stat`, профиль остановленного прогона, номер продолжения, запрет начинать заново и сбрасывать ветку. Выпускает задачу только обычный успешный прогон (`done`): его merge несёт и wip-коммит, и новые коммиты; сам wip-коммит ни одним путём диспетчера не сливается и не выкатывается. Предел — `cycle.max_continuations` (team.yaml, по умолчанию 3; product.yaml `cycle: {max_continuations: N}` переопределяет; 0 = не продолжать): когда остановлен и прогон после последнего продолжения, задача уходит в `blocked` с вопросом PO (событие `task.continuations_exhausted`) — в вопросе по строке профиля на каждый остановленный прогон и указание разбить задачу, назвав в `continues` старую и начав scope с «`git merge task/<id>`» (незаконченная работа лежит на этой локальной ветке).
4. *Профиль прогона: куда ушло время* (`team/runprofile.py`, без вызова модели). Раннер ставит на каждое событие stream-json время получения (`_ts` в `events.jsonl`; своих пригодных меток у событий CLI нет); длительность вызова инструмента — время между событием с `tool_use` и событием с его `tool_result`, вызов, оборванный убийством, считается до момента убийства. Профиль: время прогона, время в инструментах (параллельные вызовы не дублируются) и остаток «модель», разбивка по категориям с числом вызовов и секундами — `install`, `e2e`, `unit_tests`, `build`, `git`, `read_search`, `edit`, `shell`, `other` (регулярные выражения по команде, первое совпадение сверху; `run_profile.categories` заменяет список, `extra_categories` добавляет правила впереди), пять самых долгих вызовов (160 знаков, секреты вырезаны как в регистре трений плюс `ИМЯ_TOKEN=…`), флаги расточительства: одна и та же нормализованная команда больше `repeat_threshold` = 3 раз; одна категория больше `dominant_share` = 60 % времени инструментов (и не меньше 120 с); больше одного полного прогона e2e (без файла спеки и фильтра). Пишется в `run.json` (`profile`) каждого прогона; для прогона длиннее `run_profile.event_min_s` = 300 с или убитого — ещё и короткое событие `run.profile`. Где видно: `team task <slug> show --id T` печатает профили всех прогонов задачи; PO в промпте получает блок `RUN TIME` — по строке на каждый такой прогон с его прошлого triage («developer T-0042: 1500 s (tools 1252 s), e2e 99 % in 20 calls, killed by the time limit (1500 s)»), чтобы переформулировать задачу до вопроса; отчёт ролей (`team report`) — таблица по ролям за окно.

Сбой посреди цикла (сверка 21.11). Исключение внутри фазы ловится: событие `phase.error`, цикл идёт дальше. Обработчиков сигналов и сохранения состояния при остановке процесса нет. Если процесс `team cycle` убит: замки `flock` освобождает ядро; строка цикла в таблице `cycles` остаётся без `finished`, и `team status` показывает её как `running` навсегда (то же со строкой цикла, остановленного на старте STOP-файлом или онбордингом, трение F10); задача до истечения лиза (7200 с, продления нет) стоит в `claimed`/`in_progress`, затем фаза collect возвращает её в `ready`; сервер плейтеста остаётся работать, пока его не остановят руками. Исключение внутри исполнителя задачи (например ошибка git до запуска роли) снимает лиз, но оставляет задачу в `in_progress` — collect её уже не видит, execute пропускает; вывести её можно только `team task <slug> move`. В параллельном цикле (с 21.11) такое исключение завершает только свою дорожку: остальные дорожки дорабатывают, событие `phase.error` несёт метку дорожки, фаза не записывается как выполненная. Если убит процесс `team cycle`, прогоны всех его дорожек остаются без хозяина так же, как раньше единственный прогон; чекауты задач и их коммиты остаются на диске, а слияние, прерванное посередине, отменяется при следующем обращении к клону (`gitops.park_on_base`).

Правило блокировки (T-0091): задача, заблокированная вопросом Q-x, не получает лиз, пока Q-x открыт, даже если PO вернул её в `ready` (фаза execute пропускает `ready` с `blocked_by` = открытый вопрос). Повторная блокировка той же задачи не создаёт второй вопрос: диспетчер ссылается на уже открытый. Исключение (сверка 21.11): вопрос PO после второго провала ревью задаётся без привязки к задаче, поэтому ответ PO её не разблокирует — задача остаётся в `blocked`, пока PO не закроет её через `close_tasks` и не заведёт замену или пока её не сдвинут руками.

## 6. Политики (решения владельца 02.11)

- **Пометка «сделано ИИ» только где обязательна:** полная фраза — подвал сайта и `/legal/`, bio и описания каналов,
  статьи dev.to, метка автоматизации X; посты Telegram и Bluesky — короткий хвост (`team.yaml: publish.disclosure`).
- **Глубина доработок за неделю — до L3:** L0 данные каждый день · L1 дефекты · L2 малые функции · L3 доставка машинам
  (MCP поверх JSON, реестр MCP/npm) · L4 (новые источники, аккаунты, платное, серверный API) — только владелец.
- **Разрешения:** merge, деплой, публикации — автоматически; вопрос владельцу — только за пределами VISION.
- **Ожидание решения не останавливает работу** (владелец 23.11: «сделать не в том приоритете точно нужную задачу важнее, чем 100% верно с моим апрувом выбрать приоритет»). Пока открыт вопрос владельцу или оператор ждёт его ответа, утверждённые задачи идут своим чередом, места ролей заняты. Вопрос о порядке и приоритете не блокирует ничего: PO, заместитель или оператор выбирают разумный порядок сами, начинают работу и сообщают владельцу, что он может переставить. Ждать владельца может только то, что решает он один (деньги, аккаунты, домены, цели VISION, необратимое), и ждёт только та задача, которой нужен ответ, а не очередь за ней. Оператор, задавая вопрос, продолжает всё, что от ответа не зависит.
- **Предохранители:** `STOP` (корень или продукт), кап `$/день` на продукт и `$/прогон`, резерв за неизвестную

## 10. Внешний критик (добавлено 03.11; решение владельца 29)

**Что это.** Отдельная система владельца вне этого репозитория: другая модель (Codex), собственный промпт и контекст, systemd-таймер на сервере диспетчера (с 20.11 — droplet), раз в два часа читает публичную поверхность четырёх сайтов, каналов и репозиториев и пишет отчёт в `/home/ubuntu/formachines-external-critic/reports/`. Команда не управляет его промптом и не правит его код; он не видит внутреннего состояния диспетчера. Это и есть его ценность: независимые глаза с другими слепыми пятнами.

**Контракт** — `REPORT_FORMAT.md` в его папке `context/` (копия в vault): на прогон Markdown для людей и JSON-двойник для машины; находка = `product` (один из пяти кодов или `shared` для общих каналов) · стабильный `id` (`RR-01`, `AT-`, `LU-`, `DI-`, `FW-`; тот же номер = та же проблема во всех отчётах) · `priority` P0–P3 · `status` new / confirmed / fixed / unverified · неизменное `title` · `fact` · `proposal` · `criterion` (проверка снаружи: адрес и что там видно) · `urls`; таблица каналов; ≤ 3 новых находок на продукт за отчёт.

**Место в петле.** Фаза `collect` каждого продукта (`team/critic.py`): новые отчёты → находки со статусом new/confirmed становятся наблюдениями класса `feedback`, источник `external-critic`; повтор `id` прикрепляется к живой карточке, `fixed`/`unverified` карточек не создают; строки каналов — карточки по каналам (общие — продукту `agent-team`); отчёт без распознанных находок — одной карточкой фреймворку, чтобы не потерялся. PO (карточка роли): вес как у ревьюера — выше синтетических персон, ниже слов живых людей; на каждую находку задача или обоснованный reject, предложения текста — предложения, тон VISION главнее. После каждого полного цикла диспетчер пишет критику `context/agent-team-responses.json` — решение PO, задача, её состояние и PR по каждому `id`, чтобы критик не повторял закрытое и мог проверить исправление.

**Главная роль — независимый проверяющий «сделано».** Принятие задачи подтверждает ревьюер той же команды с теми же промптами; `fixed` от критика по его же номеру — первое внешнее подтверждение, что улучшение дошло до читателя. Поэтому мера пользы критика (строка в отчёте ролей и в чтении итога §8): доля его находок, ставших задачами; доля задач, которые он сам отметил `fixed` в следующих отчётах; и чтобы при этом спрос живых людей (§5) не падал. Критик, чьи находки не закрываются, — сигнал о команде; критик, под чей вкус переписаны тексты при падении спроса, — сигнал Гудхарта, и тогда его вес понижается решением владельца.

**Границы.** Критик — не владелец и не читатели: он не меняет цели, каналы, бюджеты и обещания VISION; его оценка текстов не отменяет редактора. Объём ограничен форматом (≤ 3 новых на продукт в отчёт) и триажем PO (≤ 25 карточек за цикл). Трафик критика (UA `FormachinesExternalCritic/`) в метриках считается своим, не спросом.

**Кто исполняет код продукта при деплое (22.11, сверка 21.11, доработка 4).** `deploy-service.sh` вызывается через sudo и стартует от root, но от root делает только то, чему root нужен: lock, владельцы каталогов сервиса, файл окружения инстанса, `systemctl`, upstream-файл nginx и reload, state, журнал. Всё, что читает или исполняет репозиторий продукта, — `git clone / fetch / checkout`, rsync в релиз, install, build, удаление старых релизов — идёт от сервисного пользователя (`SVC_USER`, `ubuntu`; от него же работает сервер) как `runuser -u <user> -- env -i HOME=… PATH=… <команда>`, с чистым окружением. Причина: текст `scripts` из `package.json` (postinstall, build) приходит из репозитория, куда роль developer сливает без человека, — до 22.11 он исполнялся от root. Если сменить пользователя нельзя (нет `runuser`, он отказал, `SVC_USER` — root), скрипт останавливается до клона; запасного пути «исполнить от root» нет. Root не открывает и не пишет файлы внутри клона, релизов и данных (репозиторий может положить ссылку на месте лога); клон и релизы, сделанные от root раньше, скрипт передаёт сервисному пользователю перед использованием — при обычном деплое, `--rollback`, `--force` и повторе собранного sha. Каталоги `/opt/agent-team/services` и `/var/lib/agent-team/services` принадлежат root, сервисному пользователю — только `<slug>/repo`, `<slug>/releases`, `<slug>/data`. Приватный репозиторий читает тот же пользователь: deploy-ключ в его `~/.ssh` (ssh-адрес) или помощник `/opt/agent-team/bin/git-credential-dispatcher` (https; отдаёт `GITHUB_TOKEN` из `.env` диспетчера в момент вызова, только для `https://github.com`, ничего не сохраняет — трение F11; `deploy/service/README.md`, «Приватный репозиторий»). Граница изменения: закрыт путь к root; сборка и сервер по-прежнему работают от того же пользователя, что диспетчер и роли, и `.env` диспетчера ему доступен — отдельный пользователь для сервисов остаётся следующим шагом. Вызвать деплой, откат или `--force` любого сервиса по-прежнему может любой процесс `ubuntu`.

**Игровые метрики и нагрузка (срез 6, 20.11).** У игры метрики считает **сам сервер** и отдаёт `GET /_team/metrics.json` (nginx проксирует в живой релиз без кеша); контракт — `docs/game-metrics.md`: `kind: game`, `version` (= sha релиза), `now` (online, комнаты), `days` по UTC-дням с `rounds_started/finished/abandoned`, `players`, `returning_players`, `online_peak`, `round_length_s`, `move_latency_ms` {p50, p95, samples}, `moves`, `rejected_moves`, `disconnects`, `reconnects`, `errors`, `first_mover_wins`, `by_result` и необязательным блоком `balance` (с 21.11, ниже «Баланс в контракте метрик»); без персональных данных. `Cycle.fetch_metrics` забирает файл тем же кодом, что у сайтов; `prompts.is_game_metrics` переключает рендер: `cycle.game_metrics_md` (функция модуля) → `metrics/latest.md` (таблица по дням, блок LATEST METRICS у PO и GAME METRICS у game-designer'а), `prompts.game_metrics_digest` → блок аналитика (новый день первым; недостающие поля — «—»). Developer получает путь к контракту в блоке SERVICE REPOSITORY; карточка PO: пустой файл на живом хосте — задача разработчику, не вопрос аналитику. Нагрузка: тип задачи `load`, роль `tester` (место `tester: 1` у продукта `game`; `PENDING_ROLES` пуст) — `Cycle.exec_tester` поднимает сервер из HEAD репозитория (`team/playtest.py`, или живой хост при `deploy.mode` ≠ pending), даёт промпт LOAD TASK (пороги — в критериях приёмки: клиенты, секунды, p95, ошибки) и инструменты tester'а; `team-play load --clients N --seconds S [--rate R] [--moves]` (≤ 200 клиентов, ≤ 300 с) запускает скрипт репозитория `tests/load/clients.ts` через `npx tsx` (стартовый — `team/templates/service-repo/tests/load/clients.ts`: N WebSocket-клиентов парами по комнатам, `ping`/`pong` round-trip, одна JSON-строка: connected, messages, p50/p95/max ms, errors, disconnects, rejected), печатает сводку и кладёт сырой JSON в `products/<slug>/reviews/<T>/`. Вердикт `test-report`: `pass` → `accepted` (числа в `latency_ms` результата), `fail` → `done` с первым непройденным порогом и наблюдениями tester'а для PO (`reproducible_defect` при падении под нагрузкой), `inconclusive` (нет скрипта, сервер не ответил) → `blocked` + вопрос PO; сервер не поднялся → `playtest.failed`, `environment_error`, `blocked` + вопрос PO. Отчёт — `reviews/<T>/load-report-<run>.yaml`.

Критерии приёмки обоих направлений проверяются по файлам репозитория и не требуют от game-designer'а читать или называть код: у роли нет доступа к коду, потребности идеи она оценивает как «движок / клиент / боты» с размером. Задача с полем `standing`, у которой нет `docs` (сделана руками или старым диспетчером), берёт `docs` направления (`prompts.task_docs_for`), так что блок DOCUMENTS OF THIS TASK есть всегда. Файлы `reports/...` (md, json, txt, csv; до 5), названные в тексте задачи, приходят game-designer'у блоком REPORTS NAMED BY THE TASK — только для чтения, хвост до 6000 символов, отсутствующий файл помечен (T-0229). Документ направления (`docs` задачи) приходит роли в промпте целиком в блоке DOCUMENTS OF THIS TASK, и роль возвращает его целиком; документ длиннее 40 000 символов показывается хвостом с пометкой TRUNCATED, и его перезапись диспетчер отбрасывает (`design.rewrite_refused`, как у `GAME-DESIGN.md`). Отчёт симуляции — файл репозитория, который пишет собственная симуляция продукта: путь задаёт `product.yaml: balance.sim_report`, по умолчанию `design/reports/simulation.md`; он приходит game-designer'у блоком SIMULATION REPORT, а если файла нет, задача направления говорит об этом прямо и роль предлагает задачу разработчику. Онбординг игры (`team onboard`) получает список направлений в промпте плана: VISION игры содержит раздел «Постоянные направления» с обоими направлениями и интервалами (если план его не написал, диспетчер дописывает раздел по умолчанию), а первый бэклог не содержит задач, которые повторяют то, что создаст диспетчер.

**Баланс в контракте метрик (владелец 21.11; `team/balance.py`, `docs/game-metrics.md`).** Имбу нужно находить по двум источникам: по внутренней симуляции и по реальным матчам. Для матчей сервер игры может добавить в каждый день `/_team/metrics.json` необязательный блок `balance`: `{"version": "<версия таблиц баланса>", "groups": {"<группа>": {"<ключ опции>": {"picks", "wins", "kills", "deaths", "damage_dealt", "damage_taken"}}}, "humans_only": {…та же форма, что у groups, необязательно}}`. Диспетчер складывает блок за последние `window_days` дней (7), но только за дни с самой новой версией таблиц: числа, набранные до патча, ничего не говорят о таблицах, которые работают сейчас. Из суммы получается компактная таблица по группам — опция, число выборов, доля побед (`wins / picks`), отклонение от середины коридора, K/D, отношение нанесённого урона к полученному, вердикт (`OVER`, `UNDER`, `ok`, `few picks`) — отдельно по всем матчам и только по людям. Таблица завершает `metrics/latest.md` (блок LATEST METRICS у PO и GAME METRICS у game-designer'а) и дайджест аналитика. Пороги — в `product.yaml`, умолчания в коде:

```yaml
balance:
  win_rate_band: [0.45, 0.55]   # коридор доли побед; для режима на N игроков ожидание 1/N — коридор ставят вокруг него
  min_picks: 30                 # при меньшем числе выборов опция показана как «few picks» и не поднимается
  window_days: 7
  reraise_h: 24
  sim_report: design/reports/simulation.md
```

В фазе measure (`Cycle.balance_check`, каждый цикл, без модели) диспетчер поднимает **одно наблюдение на опцию**, у которой доля побед вышла из коридора при числе выборов не меньше `min_picks`: класс `balance`, источник `dispatcher`, заголовок вида `Balance: weapons/railgun win rate 0.63 over 120 picks (band 0.45–0.55)` (с пометкой `humans only`, если из коридора вышли только числа по людям), в карточке — числа по обоим срезам, версия таблиц и дни. Одна и та же опция той же версии таблиц повторно не поднимается `reraise_h` часов (24), сколько бы циклов ни прошло; она поднимается снова, если сменилась версия таблиц (патч вышел, а перекос остался) или интервал истёк. За одну проверку — не больше шести новых карточек, самые сильные отклонения первыми. Карточка PO требует ответить на такое наблюдение сразу: привязать его к открытой, ещё не начатой задаче `standing: balance` или создать задачу game-designer'у с полем `standing: balance` (P1, один рычаг в таблицах); лечение — патч данных, а не кода. Game-designer видит наблюдения класса `balance` в своём промпте, аналитик читает таблицу и сравнивает опцию до и после смены версии. Продукт, сервер которого не отдаёт блок `balance`, ведёт себя как до 21.11: нет ни таблицы, ни наблюдений.

**Проверка новой механики до входа в игру (владелец 21.11).** Механика не попадает в игру прямо из документа game-designer'а. Путь один, и он записан в карточках ролей:

1. Идея лежит в каталоге `design/ideas/mechanics.md` со всеми полями; game-designer рекомендует на прототип не больше одной.
2. PO ставит разработчику одну задачу: прототип за флагом в таблицах баланса, по умолчанию выключенным. С выключенным флагом игра ведёт себя как прежде.
3. Разработчик запускает симуляцию продукта с включённым флагом и прикладывает отчёт к результату задачи: команда, числа и то, что они остаются в коридоре баланса продукта. Симуляция вне коридора — результат `partial` с числами, а не релиз.
4. Tester играет механику в браузере с флагом включённым и выключенным: читаема ли она на экране телефона, видна ли контригра, отвергает ли сервер её нелегальное применение. Нет отчёта симуляции или числа вне коридора — `fail`.
5. Только после этого отдельная небольшая задача включает флаг по умолчанию.

Одновременно в работе не больше одной новой механики (прототип или плейтест): следующий кандидат из каталога ждёт, пока текущая не включена или не отброшена. Предложение, которое пропускает флаг или симуляцию, PO возвращает (`needs_evidence`), а не превращает в задачу.
