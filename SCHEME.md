# agent-team — схема петли, которую запускаем (единое описание)

Статус: утверждена владельцем 02.11.2026 (решения 02.11 п. 1–15 в `decisions.md` vault). Это единственное полное описание
того, что работает; ТЗ v2 в vault — история проектирования, README — команды. Меняется только вместе с решением владельца.

## 1. Что это

Диспетчер (Python: файлы + git + SQLite) ведёт продукт силами ИИ-ролей на Claude Code. Роли — короткие прогоны
`claude -p` без памяти; между собой не разговаривают, всё общение — записи в `products/<slug>/` (задачи, вопросы,
наблюдения, ревью, дайджесты). Диспетчер — программа: очередь, лизы, бюджеты, фазы, разрешения, журнал. Решения о продукте
принимает роль PO внутри `VISION.md`; за пределами VISION (цели, каналы, бюджет, обещания, аккаунты, домены) — вопрос владельцу.

## 2. Роли

| analyst | метрики по логам, эффект принятых задач, прогресс к целям, SEO/GEO-срезы | только чтение метрик (в промпте); ни shell, ни curl/fetch любого URL — проверки живого сайта идут в `friction` или `need_hypothesis` для reviewer | `analyst-report` + наблюдения | PO |
| marketer | ведёт каналы продукта: **план недели** (`plan: true` → `products/<slug>/marketing-plan.md`: каналы, рубрики, слоты с датами UTC и целью G1–G5, что убрать, почему) и посты по слотам плана; в промпте — память: опубликованное за 7 дней (канал, дата, ссылка, задача, 120 символов текста из таблицы `posts`), переходы по каналам `by_src` из метрик сайта за 14 дней с правилом «две недели без переходов → реже, переходы есть → чаще», ответы людей за 7 дней, текущий план; карточка роли содержит стратегию каждого канала (аудитория, формат, частота, цель VISION); тред ответов в канале считается одним постом для дневного лимита; ссылки на ещё не существующую статью dev.to нет (ссылка на страницу продукта или без неё); метку ИИ ставит `team-publish`, в черновик её не пишут | `team-publish` (лимиты, пометка и метка источника ставятся инструментом), `team-fetch` (хосты: сайт продукта, `extra_hosts` продукта — у diary formachines.ai (errata и др.) и порталы bymachines.ai и др., у luz-amanha threads.com для проверки, что пост уже есть; перечисленный хост открывается вместе со всеми поддоменами, включая `www.`, но не по совпадению суффикса, — каналы публикации и github.com, raw.githubusercontent.com), `Write` (файл поста и файл плана создаются только Write: heredoc, перенаправления, python3, Edit запрещены) | `task-result` со ссылками на посты; у план-задачи — файл плана, постов нет | диспетчер записывает посты (с текстом); план-задачу принимает по файлу (≥ 200 символов), без поста |

## 3. Цикл (cron раз в час на каждый продукт, `team cycle`)

| Фаза | Что делает | Модель |
|---|---|---|
| collect | снимает истёкшие лизы; забирает `/_team/metrics.json` сайта; **собирает обратную связь** (GitHub Issues, ответы/упоминания Bluesky) в наблюдения и **отвечает людям** (роль support, в рамках VISION); раз в N циклов — персоны; раз в 12 ч — программная SEO-проверка | persona |
| review | задачи `released` (после паузы на деплой) → reviewer → `accepted` / `in_progress` (fail, ≤ 2) / `blocked` + вопрос PO | reviewer |
| triage | при новых наблюдениях, вопросах к PO, простое команды или **простое разработчика** (нет его задач; не чаще раза в `cycle.dev_idle_po_every_h` = 6 ч, PO ставит дефекты и задачи качества) → PO; в начале фазы — карточки `hypothesis_readout` для фич, чей `read_on` наступил | po |
| execute | одна задача: developer (повтор задачи продолжает существующую ветку `task/<id>` с коммитами прошлой попытки, слив в неё base; при конфликте слияния — слияние с приоритетом стороны прошлой попытки, коммит прошлой попытки остаётся в истории ветки) → коммит → **merge в main + push** → droplet публикует ≤ 5 мин → `released`; marketer → черновики (`team-publish` в режиме черновика) → editor → при revise одна доработка маркетолога → editor → диспетчер публикует одобренное (текст поста — в таблицу `posts`) → `accepted`; marketer с `plan: true` → пишет `marketing-plan.md` в рабочей папке → диспетчер копирует в `products/<slug>/` → `accepted` без поста (файла нет или < 200 символов → вопрос PO); analyst-задача → `done` | developer / marketer / analyst |
| measure | каждые 6 ч (`measure_every_h`): analyst по метрикам, эффект задач → `measured` → `done` | analyst |
| geo | раз в 168 ч: geo-probe | geo-probe |
| voice | раз в 84 ч, два раза в неделю (`cycle.voice_every_h`): voice, темы — `product.yaml: voice_topics` или умолчания по продукту | voice (Opus) |
| collect (внешний критик) | каждый цикл: новые отчёты `external_critic.dir` (сторонняя система, Codex, раз в 2 ч) → находки `**ID · Pn · заголовок**` разносятся по продуктам (токен id, заголовок секции, хост) → наблюдения `feedback`/`external-critic`, повтор id — к живой карточке; отчёт без находок — одной карточкой фреймворку. PO отвечает задачей или обоснованным reject (владелец 03.11: «критика ещё одного ревьюера») | — |
| digest | в 07 и 19 UTC: сводка в `digests/` и в Telegram ops | — |
| (вне цикла) отчёт ролей | cron 07:30 и 19:30 UTC, `team report`: ведомость за 12 ч по продуктам и ролям из хранилища → один прогон `reporter` → абзац от первого лица на каждую работавшую роль + «что выбрал и что реализовано» от PO → Telegram ops; файл `data/reports/<stamp>.md` с ведомостью для проверки | reporter |

**Правило гипотез** (владелец 07.11, `team/hypothesis.py`): задача типа `feature` от PO несёт гипотезу — кто, боль словами людей, доказательства, изменение, ожидаемый эффект, метрика, `min_sample` (сколько живых людей нужно, чтобы прочитать эффект), `read_on` (будущая дата) и оценка reach × pain × confidence × ease (1–5). Доказательство — хотя бы одно от живых людей: `voice:<дата>:P#`, наблюдение класса `feedback`/`voice` или внешняя ссылка на слова человека; персоны, внешний критик, ревьюер и метрики сами по себе не считаются. Без этого фича создаётся в `proposed`, а готовая фича без гипотезы перед стартом возвращается в `proposed`; PO поднимает её через `promote_tasks`, когда появилось доказательство. Когда наступает `read_on` принятой фичи, диспетчер кладёт PO одно наблюдение `hypothesis_readout`: подтвердилась / опровергнута / мало людей. Вне правила — дефекты, задачи качества, контент, маркетинг, задачи аналитика, задачи владельца и ретро.

**Правило качества** (владелец 08.11): разработчик не простаивает, пока что-то сломано или измеримо хуже, чем должно быть. Тип `defect` — сломано или неправда; тип `quality` — то же самое, сделанное лучше без нового обещания: скорость, упавшие проверки SEO/GEO, вёрстка на 375 px, доступность, понятность того, что уже есть, полнота данных. В `problem` — источник (упавшая проверка, провал ревью, `ux_friction` персоны, находка критика, URL и что видно). Если у разработчика нет задач, диспетчер будит PO не чаще раза в `cycle.dev_idle_po_every_h` (6 ч) с просьбой поставить 1–2 такие задачи; новая страница, раздел или возможность — это `feature` под правилом гипотез.

Правило PO (T-0042): задача, критерии которой выполнимы без правки репозитория (ежедневная проверка данных, «Check:»), — задача analyst (или тип `check`) либо называет файл для правки; developer-задача без ожидаемого коммита — дефект задачи (F-0104, F-0107, F-0109, F-0110, F-0113).

Правило PO (T-0064): перед постановкой задачи PO сверяет имена полей и объектов в критериях с ограничениями самой задачи (например, «без переименования» против «объект `sample`»); при конфликте в тексте задачи сказано, что главнее (пример: T-0077, F-0134; также F-0132).

Правило triage: PO видит `not_before` каждой задачи бэклога; предложенная задача с тем же названием или с той же парой «роль + `not_before`», что у открытой, не создаётся (событие `task.duplicate_skipped`, строка в дайджесте PO). PO закрывает лишние задачи через `close_tasks` → `rejected`.

Правило «новый инструмент пробуется в день появления» (владелец 03.11): новый канал в `product.yaml`, новый флаг инструмента, новый файл данных — PO ставит первую настоящую пробу в ближайший цикл (`not_before` = сейчас), а не в план на следующие дни; результат пробы идёт в план. Инструмент, пролежавший сутки без пробы, — дефект PO.

Опыт читателя — цель, а не побочная проверка (решение владельца 32, 04.11: «персоны на Opus, фокус на user experience, интересе и пользе; нельзя, чтобы только внешний критик работал на это»): персоны запускаются дважды в день на продукт по 2 сценария в ротации; их оценки копятся, PO видит средние и желания и при интересе или пользе ≤ 3 ставит хотя бы одну задачу за цикл на интерес и пользу раньше внутренних улучшений. Находки персон `ux_friction`/`value_gap` весят как находки внешнего критика. Ни персоны, ни критик не спрос: первым остаются счётчик людей и слова живых людей.

Заместитель владельца (`deputy`, мандат `DEPUTY.md` — защищённый путь): вопрос владельцу, открытый дольше `deputy.after_h`, получает ответ по мандату — `decided` (консервативный выбор внутри VISION), `unavailable` (секреты, деньги, аккаунты, каналы, цели VISION: «недоступно до возвращения, действуй без этого или закрой задачу») или `info`; задача выходит из `waiting_owner`. Введено 03.11 на неделю отъезда владельца (решение 27).

Правило повтора: если developer вернул `partial` и его friction (наборы `kind`) пересекается с предыдущей попыткой (общий вид `kind`; `environment` не считается, если есть другие виды; полное равенство наборов не требуется) (или совпал summary / текст friction), задача сразу `blocked`, PO получает вопрос; третий почасовой запуск не стартует (T-0024).

Места в execute: `cycle.execute_slots` — по одному месту на роль за цикл (developer 1 · marketer 1 · analyst 1; product.yaml может переопределить), чтобы ежедневный пост не голодал за задачами разработчика (03.11). Маркетинговая задача без записанной публикации ревьюером не принимается — `blocked` и вопрос PO; исключение — план-задача (`plan: true`), её приёмка — наличие `marketing-plan.md`.

Маркетинг по плану (03.11, оценка сессии каналов: роль была реактивна — одна задача = один пост, без плана, памяти и обратной связи): `products/<slug>/marketing-plan.md` — неделя по каналам; PO создаёт план-задачу, когда плана нет или он старше 7 дней, и режет слоты плана на пост-задачи с `not_before`; маркетолог в каждом прогоне видит опубликованное за 7 дней, переходы по `?src=` за 14 дней с вердиктом по каналу и слова людей; `metrics/latest.md` показывает строку `Visits by ?src=`.

Фаза execute, «сделано, но ничего не закоммичено» (T-0038): первый такой результат возвращает задачу в `ready`, а в заметке перехода (её читает `friction.py`, вид `no_commit`) лежат резюме developer и начало `self_check`. Второй подряд — задача сразу `blocked`, PO получает вопрос «переформулировать, разбить или закрыть»; третий запуск не стартует. Записи считаются по всей истории задачи (T-0043): если PO вернул в `ready` задачу с двумя такими записями, developer её не запускает (охрана `guard_no_commit_loop`, T-0046: проверяется в любом состоянии — ready, in_progress, claimed — и ещё раз в `execute_task`) — заголовок на «Check:» превращается в задачу типа `check` для analyst, остальное снова `blocked` с вопросом к PO (F-0103, F-0104, F-0107–F-0109). Исключение (T-0041): если в результате `done` без коммита есть непустое `no_change_reason` и хотя бы один пункт `self_check` с `met` и свидетельством, это «уже выполнено»: запись `no_commit` не создаётся, задача уходит в `review` (или сразу в `accepted`, если PO дал ей тип `check`) (F-0103, F-0104, F-0107–F-0110, F-0112, F-0113).

Гварды результата (03.11 вечер): `partial`, повторивший предыдущий (тот же итог или те же трудности), блокирует задачу с вопросом PO — не крутится дальше; результат-заглушка аналитика (короче 120 знаков или «дубликат вызова / см. предыдущий отчёт») не закрывает задачу — `blocked` + вопрос PO. Зеркало гварда «контент без поста не принимается».

Правило `depends_on` (T-0027): необязательное поле задачи — список id; готовая задача не запускается, пока каждая зависимость не в состоянии `accepted`/`measured`/`done` с непустым (не заглушечным: ≥ 120 символов, без «дубликат вызова» и т. п.) последним результатом; неизвестный id = не выполнено. Правило повторного partial: второй подряд `partial` (или `partial` после `blocked`) с общим видом трудности (`environment` игнорируется, если есть другие виды) либо с тем же резюме блокирует задачу и задаёт вопрос PO; проверка выполняется до проверки «ничего не закоммичено», поэтому partial без коммитов тоже считается; третий запуск не стартует.

Правило execute: готовая задача, в названии которой есть дата `ДД.ММ` позже сегодняшней (UTC), но нет `not_before`, не запускается; диспетчер пишет наблюдение для PO (поставить `not_before`). Задача, дважды заблокированная одним и тем же вопросом, не перезапускается автоматическим (не владельческим) ответом без `not_before`; событие `task.restart_suppressed`.

Состояния задачи: `proposed → ready → claimed → in_progress → review/released → accepted → measured → done`;
боковые `blocked`, `waiting_owner`, `rejected`, `deferred`. Каждый переход — в `history[]` задачи.

## 9. Самоулучшение фреймворка (добавлено 02.11 вечером; вопрос владельца «копит ли сложности без меня»)

Три уровня, каждый — без владельца, кроме последнего шага:

1. **Регистр трудностей** (`team/friction.py`, `data/framework/friction.jsonl` + `register.md`, глобально по продуктам).
   Детерминированно из записей диспетчера: упавшие прогоны (`run_failed`), отказанные инструменты (`tool_denied`, из
   `permission_denials` прогона — с текстом отказанной команды/URL до 80 символов), а в транскрипт прогона диспетчер пишет раздел «Denied calls» с разрешённой формой — Write для файлов, голый `team-fetch` с `--json-path/--count/--grep` вместо пайпов (T-0020; `<`/`>` в аргументе team-fetch читается как редирект, T-0031 подсказывает grep без них и `--around N≥1`), ошибки фаз, стопы бюджета, задачи в `blocked`, истёкшие лизы, «сделано, но не
   закоммичено», провал/неясность ревью, вопросы владельцу старше 24 ч, наблюдения `environment_error`. Плюс то, что роли
   сами пишут в поле `friction` своих отчётов (task-result, review-verdict: не хватило инструмента, отказ в разрешении,
   непонятная инструкция, схема не подошла, нет данных). Собирается в конце каждого прогона `team cycle --product all`;
   Откат кода (T-0061): в начале `team cycle --product all` диспетчер сравнивает HEAD чекаута с записанным в прошлый раз
   (`data/framework/last-head`); если новый HEAD — предок прежнего (сторож вернул код к `last-good`), в регистр попадает
   одна запись вида `rollback` со списком сброшенных коммитов (хеш и заголовок) в `summary` и поле `dropped`. Обычное
   движение вперёд и неизменный HEAD записи не создают (voice:2026-11-07:P8).
   `team friction` печатает регистр, `--out` пишет публичный срез (счётчики, короткие строки, секреты вырезаны) для дневника.
2. **Ретро** (`team/retro.py`, роль `framework-retro`, раз в `framework.retro_every_h` = 24 ч): читает регистр за 7 дней,
   SCHEME.md и карточки ролей, группирует по причинам, пишет предложения с доказательствами, файлами, критериями приёмки и
   риском. Отчёт — `data/framework/retro/<дата>.md`; каждое предложение — GitHub Issue в `OOuph/agent-team` с меткой
   `friction` (дедупликация по заголовку). Это и есть «копить без владельца»: список виден в GitHub, не на сервере.
   В отчёт добавляется раздел `## Spend` (`retro.spend_section`, T-0056): расход за каждый из последних 7 дней (UTC) из общего учёта диспетчера (`billing`-ledger) рядом с лимитом всей команды — суммой `budget_usd_per_day` всех продуктов (`framework.spend_cap_usd` переопределяет) — и с расходом кредитов (реальные деньги, лимит $100 в сутки); дни выше 80 % помечены `OVER 80%`. Нет записи о расходе — `spend: n/a` и запись `missing_data` в регистр, числа не выдумываются.
   В начале отчёта стоит `## Owner digest` (`retro.owner_digest`, T-0062, не более 12 строк, по одной строке на пункт в таком порядке): PR, слитые за 24 ч (номера и заголовки); PR, ждущие человека (затронуты `framework.protected_paths` или изменены/удалены тесты без строки `tests-change-reason: F-xxxx`); откаты к last-good за 24 ч (записи регистра вида `rollback`); расход сегодня против лимита. Пустой пункт — `none`, нечитаемый источник (GitHub, учёт расхода) — `unknown`, ничего не угадывается.
3. **Правки** — продукт `agent-team` (`products/agent-team/`, `repo.mode: pr`): предложения любого риска
   (`framework.task_risks`) становятся задачами; developer делает их на ветке `task/<id>`, диспетчер гоняет
   `repo.test_cmd` (pytest), при зелёных тестах пушит ветку и открывает pull request. Push и `POST /pulls` при HTTP 5xx GitHub повторяются 3 раза с паузой (5, 15, 45 с; перед повтором ветка ищется среди открытых PR); если и после этого 5xx — задача возвращается в `ready` с событием `pr.transient_failure`, а не в `blocked`: коммит цел (F-0100); но не более 3 раз подряд (поле задачи `transient_failures`, `gitops.MAX_TRANSIENT`): на третий раз задача уходит в `blocked` с причиной «5xx N times in a row». Распознаются формы «returned error: 5xx», «HTTP 5xx», «HTTP Error 5xx», «HTTP/2 5xx», «status 5xx», «remote: … 5xx»; 4xx не повторяется (F-0100). Дальше (решение владельца 02.11,

   `framework.canary_product` на коде кандидата (`PYTHONPATH` = ветка) на КОПИИ состояния продукта (с 03.11: первая версия гоняла настоящий цикл на живом состоянии и публиковала/мержила реальные задачи); прошёл все фазы
   без ошибок → диспетчер сам сливает PR через API и fast-forward'ит свой чекаут (сервер работает из git-клона);
   не прошёл → `waiting_owner`, PR открыт с логом. **Запретный список** `framework.protected_paths`: PR, трогающий его,
   ждёт человека. С 03.11 (решение владельца 24a: «на этапе пилота на риски не смотрим, максимальную автоматизацию
   делаем») в списке только пара отката — `run-cycle.sh` и `watchdog.sh`: это то, что отменяет плохое самослияние, без
   них автоматизация теряет страховку. Всё остальное (`store.py`, `runner.py`, `config.py`, `publish.py`, `team.yaml`,
   `build-site.sh`, `deploy/`, `bin/`) сливается само после тестов и канарейки; до 03.11 ждало человека.
   **Ворота тестов** (T-0058): PR, который изменяет или удаляет файл в `tests/` (добавление новых файлов не считается), сливается сам только если в теле PR есть строка `tests-change-reason: F-xxxx …` с id записи регистра; строка стоит отдельной строкой в `summary` результата разработчика (из него диспетчер собирает тело PR; правило в карточке `team/roles/developer.md`, T-0059); иначе (или если id нет) задача уходит в `waiting_owner`, PR ждёт человека (`gitops.tests_modified_or_deleted`, `gitops.has_tests_change_reason`, `Cycle.release_as_pull_request`).

Если в `summary`/`changes` названы файлы, которых нет в диффе, добавляется строка `MISMATCH` и пишется запись трения (событие `pr.claim_mismatch` → реестр).

## 10. Внешний критик (добавлено 03.11; решение владельца 29)

**Что это.** Отдельная система владельца вне этого репозитория: другая модель (Codex), собственный промпт и контекст, systemd-таймер на reservememes, раз в два часа читает публичную поверхность четырёх сайтов, каналов и репозиториев и пишет отчёт в `/home/ubuntu/formachines-external-critic/reports/`. Команда не управляет его промптом и не правит его код; он не видит внутреннего состояния диспетчера. Это и есть его ценность: независимые глаза с другими слепыми пятнами.

**Контракт** — `REPORT_FORMAT.md` в его папке `context/` (копия в vault): на прогон Markdown для людей и JSON-двойник для машины; находка = `product` (один из пяти кодов или `shared` для общих каналов) · стабильный `id` (`RR-01`, `AT-`, `LU-`, `DI-`, `FW-`; тот же номер = та же проблема во всех отчётах) · `priority` P0–P3 · `status` new / confirmed / fixed / unverified · неизменное `title` · `fact` · `proposal` · `criterion` (проверка снаружи: адрес и что там видно) · `urls`; таблица каналов; ≤ 3 новых находок на продукт за отчёт.

**Место в петле.** Фаза `collect` каждого продукта (`team/critic.py`): новые отчёты → находки со статусом new/confirmed становятся наблюдениями класса `feedback`, источник `external-critic`; повтор `id` прикрепляется к живой карточке, `fixed`/`unverified` карточек не создают; строки каналов — карточки по каналам (общие — продукту `agent-team`); отчёт без распознанных находок — одной карточкой фреймворку, чтобы не потерялся. PO (карточка роли): вес как у ревьюера — выше синтетических персон, ниже слов живых людей; на каждую находку задача или обоснованный reject, предложения текста — предложения, тон VISION главнее. После каждого полного цикла диспетчер пишет критику `context/agent-team-responses.json` — решение PO, задача, её состояние и PR по каждому `id`, чтобы критик не повторял закрытое и мог проверить исправление.

**Главная роль — независимый проверяющий «сделано».** Принятие задачи подтверждает ревьюер той же команды с теми же промптами; `fixed` от критика по его же номеру — первое внешнее подтверждение, что улучшение дошло до читателя. Поэтому мера пользы критика (строка в отчёте ролей и в чтении итога §8): доля его находок, ставших задачами; доля задач, которые он сам отметил `fixed` в следующих отчётах; и чтобы при этом спрос живых людей (§5) не падал. Критик, чьи находки не закрываются, — сигнал о команде; критик, под чей вкус переписаны тексты при падении спроса, — сигнал Гудхарта, и тогда его вес понижается решением владельца.

**Границы.** Критик — не владелец и не читатели: он не меняет цели, каналы, бюджеты и обещания VISION; его оценка текстов не отменяет редактора. Объём ограничен форматом (≤ 3 новых на продукт в отчёт) и триажем PO (≤ 25 карточек за цикл). Трафик критика (UA `FormachinesExternalCritic/`) в метриках считается своим, не спросом.
