# agent-team — схема петли, которую запускаем (единое описание)

Статус: утверждена владельцем 02.11.2026 (решения 02.11 п. 1–15 в `decisions.md` vault). Это единственное полное описание
того, что работает; ТЗ v2 в vault — история проектирования, README — команды. Меняется только вместе с решением владельца.

## 1. Что это

Диспетчер (Python: файлы + git + SQLite) ведёт продукт силами ИИ-ролей на Claude Code. Роли — короткие прогоны
`claude -p` без памяти; между собой не разговаривают, всё общение — записи в `products/<slug>/` (задачи, вопросы,
наблюдения, ревью, дайджесты). Диспетчер — программа: очередь, лизы, бюджеты, фазы, разрешения, журнал. Решения о продукте
принимает роль PO внутри `VISION.md`; за пределами VISION (цели, каналы, бюджет, обещания, аккаунты, домены) — вопрос владельцу.

## 2. Роли

| Роль | Отвечает за | Инструменты | Результат | Кто принимает |
|---|---|---|---|---|
| PO | наблюдения и цели → задачи с критериями приёмки; `repo_only: true`, если критерии называют файлы репозитория (mcp/, тесты, README, код) — ревьюер получит чекаут (если PO не поставил, диспетчер сам ставит его, когда `how_to_verify` разработчика содержит только URL `raw.githubusercontent.com`); ответы ролям; приоритеты; дайджест; **ведёт маркетинг по плану**: видит `marketing-plan.md`, переходы по каналам (`?src=`) и посты за 7 дней; нет плана или он старше 7 дней → одна план-задача (`plan: true`), есть план → режет слоты на пост-задачи с `not_before` | только чтение файлов продукта (в промпте) | `po-decision`: решения, ≤ 3 Ready (у маркетинговой — признак `plan`), вопросы владельцу, дайджест | владелец читает дайджест |
| developer | одна задача за цикл в чекауте репозитория сайта: код, контент, сборка `public/` | файлы и git в чекауте; без деплоя и сети к продакшену | коммит на ветке `task/<id>` + `task-result` | диспетчер мержит, reviewer проверяет |
| reviewer | независимая приёмка на живом сайте по каждому критерию | `team-fetch` (GET, `--grep` [`--around N`, `--count`], `--tail`, `--offset K`); задача с `repo_only: true` — ещё read-only чекаут влитого коммита: `Read`/`Glob`/`Grep` и фиксированные `python3 -m unittest [discover]`, `python3 -m pytest -q`, `git log -1` (без записи и сети, кроме `team-fetch`) | `review-verdict`: pass / fail / inconclusive с цитатами; при `repo_only` тесты прогоняются в чекауте и дают pass/fail; иначе критерий, требующий чекаута или процесса, — в `limits` как `not observable: repo-only`, без повторного inconclusive на ревью; негативный кейс, который нельзя получить на живом сайте, — в `limits` как `not observable`, а не inconclusive, если остальные критерии прошли | автор свою работу не принимает |
| analyst | метрики по логам, эффект принятых задач, прогресс к целям, SEO/GEO-срезы | только чтение метрик (в промпте) | `analyst-report` + наблюдения | PO |
| marketer | ведёт каналы продукта: **план недели** (`plan: true` → `products/<slug>/marketing-plan.md`: каналы, рубрики, слоты с датами UTC и целью G1–G5, что убрать, почему) и посты по слотам плана; в промпте — память: опубликованное за 7 дней (канал, дата, ссылка, задача, 120 символов текста из таблицы `posts`), переходы по каналам `by_src` из метрик сайта за 14 дней с правилом «две недели без переходов → реже, переходы есть → чаще», ответы людей за 7 дней, текущий план; карточка роли содержит стратегию каждого канала (аудитория, формат, частота, цель VISION) | `team-publish` (лимиты, пометка и метка источника ставятся инструментом), `team-fetch`, `Write` (файл поста и файл плана создаются только Write: heredoc, перенаправления, python3, Edit запрещены) | `task-result` со ссылками на посты; у план-задачи — файл плана, постов нет | диспетчер записывает посты (с текстом); план-задачу принимает по файлу (≥ 200 символов), без поста |
| editor | вычитывает каждый черновик маркетолога до публикации: оценки 1–5 (крючок, ясность, конкретика, тон, честность), approve с лёгкой правкой / revise один раз / reject; пишет уроки в `editorial-lessons.md` | `team-fetch` | `editor-review`; оценки в `data/editorial/scores.jsonl`, средний балл в дайджесте, падение < 3.5 → наблюдение PO | PO; владелец видит балл в дайджесте |
| persona | играет пользователя по карточке (слепая) | `team-fetch` | `persona-result` + наблюдения | PO отделяет синтетику от фактов |
| geo-probe | раз в неделю контрольные вопросы ИИ-поиску: цитируют ли нас | WebSearch, WebFetch | `geo-report` + наблюдения + `metrics/geo-*.json` | analyst, PO |
| support | отвечает людям (GitHub issues/комментарии, ответы и упоминания в Bluesky) в рамках VISION и живого сайта; за рамками — вопрос PO; ≤ 10 ответов в день | `team-fetch` | `support-reply` → комментарий в issue / ответ в Bluesky с пометкой ИИ | PO видит ту же карточку обратной связи |
| framework-retro | каждый цикл (`framework.retro_every_h: 1`) читает регистр трудностей фреймворка и предлагает правки фреймворка (не продуктов) | Read, Glob, Grep в репозитории фреймворка | `retro-report`: предложения с доказательствами F-xxxx, файлами, критериями; issues `friction`; задачи в продукт `agent-team` | владелец (merge PR) |

Добавить роль = карточка `team/roles/<role>.md` + схема `team/schemas/<x>.schema.json`; цикл не меняется.

## 3. Цикл (cron раз в час на каждый продукт, `team cycle`)

| Фаза | Что делает | Модель |
|---|---|---|
| collect | снимает истёкшие лизы; забирает `/_team/metrics.json` сайта; **собирает обратную связь** (GitHub Issues, ответы/упоминания Bluesky) в наблюдения и **отвечает людям** (роль support, в рамках VISION); раз в N циклов — персоны; раз в 12 ч — программная SEO-проверка | persona |
| review | задачи `released` (после паузы на деплой) → reviewer → `accepted` / `in_progress` (fail, ≤ 2) / `blocked` + вопрос PO | reviewer |
| triage | при новых наблюдениях, вопросах к PO или простое команды → PO | po |
| execute | одна задача: developer → коммит → **merge в main + push** → droplet публикует ≤ 5 мин → `released`; marketer → черновики (`team-publish` в режиме черновика) → editor → при revise одна доработка маркетолога → editor → диспетчер публикует одобренное (текст поста — в таблицу `posts`) → `accepted`; marketer с `plan: true` → пишет `marketing-plan.md` в рабочей папке → диспетчер копирует в `products/<slug>/` → `accepted` без поста (файла нет или < 200 символов → вопрос PO); analyst-задача → `done` | developer / marketer / analyst |
| measure | каждые 6 ч (`measure_every_h`): analyst по метрикам, эффект задач → `measured` → `done` | analyst |
| geo | раз в 168 ч: geo-probe | geo-probe |
| digest | в 07 и 19 UTC: сводка в `digests/` и в Telegram ops | — |
| (вне цикла) отчёт ролей | cron 07:30 и 19:30 UTC, `team report`: ведомость за 12 ч по продуктам и ролям из хранилища → один прогон `reporter` → абзац от первого лица на каждую работавшую роль + «что выбрал и что реализовано» от PO → Telegram ops; файл `data/reports/<stamp>.md` с ведомостью для проверки | reporter |

Правило triage: PO видит `not_before` каждой задачи бэклога; предложенная задача с тем же названием или с той же парой «роль + `not_before`», что у открытой, не создаётся (событие `task.duplicate_skipped`, строка в дайджесте PO). PO закрывает лишние задачи через `close_tasks` → `rejected`.

Заместитель владельца (`deputy`, мандат `DEPUTY.md` — защищённый путь): вопрос владельцу, открытый дольше `deputy.after_h`, получает ответ по мандату — `decided` (консервативный выбор внутри VISION), `unavailable` (секреты, деньги, аккаунты, каналы, цели VISION: «недоступно до возвращения, действуй без этого или закрой задачу») или `info`; задача выходит из `waiting_owner`. Введено 03.11 на неделю отъезда владельца (решение 27).

Места в execute: `cycle.execute_slots` — по одному месту на роль за цикл (developer 1 · marketer 1 · analyst 1; product.yaml может переопределить), чтобы ежедневный пост не голодал за задачами разработчика (03.11). Маркетинговая задача без записанной публикации ревьюером не принимается — `blocked` и вопрос PO; исключение — план-задача (`plan: true`), её приёмка — наличие `marketing-plan.md`.

Маркетинг по плану (03.11, оценка сессии каналов: роль была реактивна — одна задача = один пост, без плана, памяти и обратной связи): `products/<slug>/marketing-plan.md` — неделя по каналам; PO создаёт план-задачу, когда плана нет или он старше 7 дней, и режет слоты плана на пост-задачи с `not_before`; маркетолог в каждом прогоне видит опубликованное за 7 дней, переходы по `?src=` за 14 дней с вердиктом по каналу и слова людей; `metrics/latest.md` показывает строку `Visits by ?src=`.

Правило execute: готовая задача, в названии которой есть дата `ДД.ММ` позже сегодняшней (UTC), но нет `not_before`, не запускается; диспетчер пишет наблюдение для PO (поставить `not_before`). Задача, дважды заблокированная одним и тем же вопросом, не перезапускается автоматическим (не владельческим) ответом без `not_before`; событие `task.restart_suppressed`.

Состояния задачи: `proposed → ready → claimed → in_progress → review/released → accepted → measured → done`;
боковые `blocked`, `waiting_owner`, `rejected`, `deferred`. Каждый переход — в `history[]` задачи.

## 4. Обратная связь (анализ способов; решение владельца 02.11 п. 15)

| Способ | Что даёт | Навязчивость | Данные о людях | Статус в фреймворке |
|---|---|---|---|---|
| логи: клики `/go/`, 404, запросы JSON, `?src=` | спрос без слов, какой канал привёл | нулевая | нет | есть: `sitemetrics.py`, analyst |
| ссылки «полезно / нет» на карточке → `/go/vote/...` | оценка записи одним кликом | низкая | нет | задачи L2 трём сайтам |
| GitHub Issues репозитория сайта + предзаполненная ссылка «сообщить об ошибке» | разборные замечания | низкая | логин GitHub | есть: `feedback.github_issues`; ссылка — задача L2 |
| ответы, упоминания, цитаты в Bluesky | живая реакция на посты | нулевая | публичный профиль | есть: `feedback.bluesky_replies` |
| реакции в Telegram-канале | интерес к посту | нулевая | нет | analyst читает из канала; Bot API даёт счётчики только через updates — не собирается |
| опрос одной кнопкой в Telegram | ответ на один вопрос | средняя | нет | позже, решение PO |
| почта, формы, чат | длинные отзывы | высокая | да | нет: обещание «без форм и сбора данных» |

Правило PO: слова живых людей (класс `feedback`) весят больше всего; на каждое — задача или обоснованный отказ.

## 5. Аналитика: счётчики, SEO, GEO

- **Счётчики:** `sitemetrics.py` на droplet раз в час по логам nginx → классы люди / вовлечённые / возвраты / агенты /
  краулеры по именам / свои; топ страниц, referer, целевые действия, `by_src` по меткам `?src=<канал>` (их ставит
  `team-publish`). JS-счётчиков нет (обещание «без трекинга»); GoatCounter — только как L4.
- **SEO:** `sitemap.xml`, `robots.txt`, стабильные адреса, 404 с навигацией есть у всех сайтов; **IndexNow** при каждой
  публикации (droplet `publish.sh`, ключ общий, файл ключа на каждом хосте); `seocheck.py` раз в 12 ч: robots, sitemap,
  llms.txt, title/description/canonical/h1/JSON-LD/hreflang/og на выборке страниц, feed, честный 404 → дефекты в
  наблюдения. Search Console и Bing Webmaster: файл подтверждения кладёт разработчик, свойство добавляет владелец.
- **GEO:** `llms.txt`, JSON на страницу, доступ GPTBot/ClaudeBot/PerplexityBot; визиты ИИ-краулеров считаются по именам;
  `geo-probe` раз в неделю: 5 контрольных вопросов на продукт (`product.yaml: geo_queries`), цитируют ли нас, кто
  вместо нас, есть ли у нас страница под вопрос → `metrics/geo-<date>.json` + наблюдения; MCP в реестре — L3.

## 6. Политики (решения владельца 02.11)

- **Пометка «сделано ИИ» только где обязательна:** полная фраза — подвал сайта и `/legal/`, bio и описания каналов,
  статьи dev.to, метка автоматизации X; посты Telegram и Bluesky — короткий хвост (`team.yaml: publish.disclosure`).
- **Глубина доработок за неделю — до L3:** L0 данные каждый день · L1 дефекты · L2 малые функции · L3 доставка машинам
  (MCP поверх JSON, реестр MCP/npm) · L4 (новые источники, аккаунты, платное, серверный API) — только владелец.
- **Разрешения:** merge, деплой, публикации — автоматически; вопрос владельцу — только за пределами VISION.
- **Предохранители:** `STOP` (корень или продукт), кап `$/день` на продукт и `$/прогон`, резерв за неизвестную
  стоимость, inactivity-watchdog, лимит постов в канал в день, лизы задач, бэкап состояния раз в сутки.

## 9. Самоулучшение фреймворка (добавлено 02.11 вечером; вопрос владельца «копит ли сложности без меня»)

Три уровня, каждый — без владельца, кроме последнего шага:

1. **Регистр трудностей** (`team/friction.py`, `data/framework/friction.jsonl` + `register.md`, глобально по продуктам).
   Детерминированно из записей диспетчера: упавшие прогоны (`run_failed`), отказанные инструменты (`tool_denied`, из
   `permission_denials` прогона — с текстом отказанной команды/URL до 80 символов), ошибки фаз, стопы бюджета, задачи в `blocked`, истёкшие лизы, «сделано, но не
   закоммичено», провал/неясность ревью, вопросы владельцу старше 24 ч, наблюдения `environment_error`. Плюс то, что роли
   сами пишут в поле `friction` своих отчётов (task-result, review-verdict: не хватило инструмента, отказ в разрешении,
   непонятная инструкция, схема не подошла, нет данных). Собирается в конце каждого прогона `team cycle --product all`;
   `team friction` печатает регистр, `--out` пишет публичный срез (счётчики, короткие строки, секреты вырезаны) для дневника.
2. **Ретро** (`team/retro.py`, роль `framework-retro`, раз в `framework.retro_every_h` = 24 ч): читает регистр за 7 дней,
   SCHEME.md и карточки ролей, группирует по причинам, пишет предложения с доказательствами, файлами, критериями приёмки и
   риском. Отчёт — `data/framework/retro/<дата>.md`; каждое предложение — GitHub Issue в `OOuph/agent-team` с меткой
   `friction` (дедупликация по заголовку). Это и есть «копить без владельца»: список виден в GitHub, не на сервере.
3. **Правки** — продукт `agent-team` (`products/agent-team/`, `repo.mode: pr`): предложения любого риска
   (`framework.task_risks`) становятся задачами; developer делает их на ветке `task/<id>`, диспетчер гоняет
   `repo.test_cmd` (pytest), при зелёных тестах пушит ветку и открывает pull request. Дальше (решение владельца 02.11,
   поздний вечер: «запускай полную петлю и гоняй каждый час»): **канарейка** — dry-run цикл продукта
   `framework.canary_product` на коде кандидата (`PYTHONPATH` = ветка) на КОПИИ состояния продукта (с 03.11: первая версия гоняла настоящий цикл на живом состоянии и публиковала/мержила реальные задачи); прошёл все фазы
   без ошибок → диспетчер сам сливает PR через API и fast-forward'ит свой чекаут (сервер работает из git-клона);
   не прошёл → `waiting_owner`, PR открыт с логом. **Запретный список** `framework.protected_paths`: PR, трогающий его,
   ждёт человека. С 03.11 (решение владельца 24a: «на этапе пилота на риски не смотрим, максимальную автоматизацию
   делаем») в списке только пара отката — `run-cycle.sh` и `watchdog.sh`: это то, что отменяет плохое самослияние, без
   них автоматизация теряет страховку. Всё остальное (`store.py`, `runner.py`, `config.py`, `publish.py`, `team.yaml`,
   `build-site.sh`, `deploy/`, `bin/`) сливается само после тестов и канарейки; до 03.11 ждало человека.
4. **Сторож вне диспетчера** — `watchdog.sh` в cron каждые 30 минут, в запретном списке: если за 2 часа ни один цикл
   не завершился, нет STOP и нет идущего цикла → `git reset --hard` на `data/framework/last-good` (пишется `run-cycle.sh`
   после каждого удачного цикла), запись `watchdog_rollback` в регистр, сообщение владельцу в Telegram, запуск цикла.
   Остаточный риск — медленная деградация качества, которую видно по фазе измерения за дни, откат через git.

**Какой документ живёт в циклах улучшения:** этот файл (SCHEME.md) — единственное полное описание; `CHANGELOG.md` — когда и
почему он менялся (с ссылками на F-xxxx и решения владельца). Ретро обязано включать оба в файлы предложения, меняющего
поведение; developer продукта `agent-team` правит их в том же PR; дневник строит `/about/` по SCHEME. ТЗ v2 в vault —
история проектирования, README — вход для чужих.

≥ 1 PR с зелёными тестами открыт без владельца · ≥ 50 % предложений ретро владелец признал полезными.
